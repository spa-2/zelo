## 1. 목적과 범위

### 1-1. 목적
1. 예상 피크 트래픽에서 모든 도메인이 SLO를 지키는지 확인한다 (부하)
2. 트래픽을 올리면서 시스템 전체에서 **처음 막히는 자원**과 그때의 배수를 찾는다 (스트레스)
3. 한 도메인의 부하가 **다른 도메인에 주는 영향**을 수치로 확인한다
   - 로컬 채팅 스트레스에서 채팅만 늘렸는데 로그인 p95가 0.19초에서 9.3초로, 방 목록이 0.01초에서 3.4초로 늘었다 (`chat-load-test-result.md` 7장)
4. LLM은 실측 지연을 넣은 fake로 재고, 실제 OpenAI 한도가 목표 트래픽에 모자란다는 것을 결과로 남긴다 (5-0)
   - 로컬 새 기준 결과는 fake LLM(모든 호출 3.5\~6초, 의도 하나)이었다. 이번에는 작업별 실측 지연과 문장별 의도를 넣는다 (5-1, 5-2)
5. 찾은 병목을 고치고 **전·후 수치**를 남긴다

### 1-2. 범위

| 포함 | 제외 |
|---|---|
| 부하 테스트, 스트레스 테스트 (도메인별, 통합) | 스파이크, 장시간(soak), 장애 주입 테스트. 이번 범위가 아니다 |
| 사용자 API 전체 (인증, 상품, 채팅, 견적, 주문, 결제, 환불) | 관리자 API (`/api/admin/**`). 트래픽이 매우 적다. 관리자 리뷰 요약(`REVIEW_SUMMARY`)도 부르지 않는다 |
| **fake LLM** (`LLM_MODE=fake`): 모든 테스트. 지연은 2026-11-06 로컬 실제 OpenAI 부하의 작업별 실측 (5-1) | 실제 OpenAI. 이 키의 `gpt-6-luna` 한도(분당 토큰 200만)가 목표 트래픽(분당 약 320만 토큰)보다 작다 (5-0) |
| | 실제 포트원, Google·Kakao, SES. 비용과 약관 문제라 fake로 대신하고 지연 값만 실측으로 맞춘다 |
| | 포트원 웹훅. fake 모드에서는 웹훅 API(`/webhook`)가 꺼져 있어 웹훅 수신, 서명 검증, 중복 처리는 재지 않는다 |
| | 스케줄러 (배송, 주문 만료, 결제 대조). 모든 테스트에서 끈다 |
| | 프론트 화면 렌더링 시간 |

### 1-3. 로컬 새 기준 결과와 달라지는 LLM 조건

| 항목 | 로컬 새 기준 결과 (fake) | 이번 계획 (fake) |
|---|---|---|
| 의도 | `plan-intent=SHOPPING_REQUEST`로 모든 메시지가 견적 요청 | 문장 단어로 의도를 정한다 (`intent-keywords`). 견적 요청, 견적 수정, 리뷰 질문, 일반 질문이 섞인다 (5-2) |
| 메시지당 LLM 호출 | 2번 (메뉴 계획 + 견적 안내) | 의도마다 2번 (5-3) |
| LLM 응답 시간 | 모든 호출 3.5\~6초 균등 | 작업별 실측 범위 (메뉴 계획 1.1\~3.6초 등, 5-1) |
| 외부 한도 | 없음 | 없음. 실제 OpenAI의 한도(429)는 이번 테스트에서 보지 않는다 (5-0) |
| 비용 | 없음 | 없음 |

## 2. 진행 순서

| 단계 | 테스트 | 하는 일 | 찾는 것 | LLM |
|---|---|---|---|---|
| 0 | 사전 확인 (스모크) | 아주 적은 요청 | 스크립트, 시드, 환경이 맞는지. fake 지연이 설정대로 나오는지 | fake |
| 1 | 도메인별 부하·스트레스 | 도메인 하나씩 | 도메인 자체의 한계와 원인 | fake (채팅만 LLM을 씀) |
| 2 | **통합 부하** | 모든 흐름을 비율대로 섞어 피크 목표로 | 피크에서 SLO를 지키는지, 도메인 간 영향 | fake |
| 3 | **통합 스트레스** | 섞은 채로 ×1 → ×3 | 시스템 전체의 첫 병목 | fake |
| 4 | **고치고 다시 재기** | 병목 하나를 고친 뒤 2단계(통합 부하)와 3단계(통합 스트레스)를 **같은 fake 설정**으로 다시 한다 | 전·후 차이 | fake |

- 실제 OpenAI 호출은 0회다. 모든 테스트를 OpenAI 비용 없이 다시 돌릴 수 있다

### 순서를 이렇게 정한 이유
- **1단계를 2단계보다 먼저 하는 이유:** 섞은 테스트에서 느려지면 어느 도메인 때문인지 바로 알 수 없다. 도메인마다 한계와 원인을 먼저 알아 두면 통합 결과를 해석할 수 있다. 로컬 채팅 테스트에서도 단독 측정으로 견적 발급이 DB 커넥션을 1.1\~2.5초 잡는다는 원인을 찾았다
- **모든 테스트를 fake LLM으로 하는 이유:** 실제 OpenAI는 이 키의 한도(분당 토큰 200만) 때문에 채팅 목표(분당 약 320만 토큰)를 보낼 수 없다. 2026-11-06 로컬에서 실제로 보냈더니 429로 서킷이 두 번 열려 실패율 9.15%가 됐다 (5-0). 한도에 맞춰 트래픽을 낮추면 목표 트래픽을 재지 못한다. 대신 그 실행에서 잰 작업별 LLM 시간을 fake 지연으로 넣는다 (5-1). 모든 단계가 같은 LLM 조건이라 OpenAI 흔들림 없이 서버 변화만 비교된다
- **포트폴리오에서 중요한 단계:** 2 → 3 → 4. "피크 기준 통과 수치, 첫 병목, 고친 뒤 개선 폭"이 한 줄로 이어지기 때문이다

## 3. 목표 트래픽 (워크로드 모델)

### 3-1. 기본 가정

| 항목 | 값 | 근거 |
|---|---|---|
| DAU | 50,000명 | **가정.** 팀이 정한 새 기준. 상품·견적·채팅 테스트가 같은 값을 쓴다 (`load-test/product/README.md`, `load-test/quote/README.md`, `chat-session.js`) |
| 사용자당 하루 방문 | 1회 | **가정.** 장보기 앱이라 하루에 여러 번 오는 경우는 적다고 본다 |
| 피크 | 하루 트래픽의 20%가 1시간에 몰림 | **가정.** 저녁 장보기 시간대 |
| 피크 1시간 방문 | 50,000 × 20% = 10,000 | 새 기준의 "피크 1시간에 1만 명"과 같다 |
| 피크 분당 방문 | 10,000 ÷ 60분 = 166.7 | |
| 안전계수 | 1.5 | 기존 테스트와 같다. 가정이 틀렸을 때의 여유 |
| **피크 목표 (×1)** | **분당 방문 250회** | 166.7 × 1.5 |

- 예전 기준(DAU 1만, 하루의 20%가 2시간에 몰림 = 피크 2,000명)은 분당 방문 25회였다. 새 기준은 그 10배다

### 3-2. 방문 흐름(시나리오)과 비율

방문 한 번은 아래 네 흐름 중 하나다. 실제 사용자가 모두 결제까지 가지는 않으므로, 모든 사용자가 같은 사이클(로그인 → 견적 → 주문 → 결제)을 도는 방식으로 하지 않는다.

| 흐름 | 비율 | 분당 방문 (×1) | 요청 | 요청 수 |
|---|---|---|---|---|
| A. 둘러보기 | 40% | 100 | 카테고리 → 인기 상품 → 인기 검색어 → 자동완성 2번 → 검색 → 검색 2쪽 → 상세 2번 (로그인 없음, 상품 API는 인증 없이 열려 있음) | 9 |
| B. 견적·질문 | 30% | 75 | 로그인 → 방 목록 → 메시지 5개 (견적 요청, 인분 변경, 견적 수정, 리뷰 질문, 일반 질문) → 메시지 목록 | 8 |
| C. 구매 | 20% | 50 | 로그인 → 방 목록 → 메시지 3개 (견적 요청, 인분 변경, 견적 수정) → 배송지 조회 → 결제수단 조회 → 구매 확인 → 주문 생성 → 등록 카드 결제 → 주문 상세 | 11 |
| D. 내 주문 확인 | 10% | 25 | 로그인 → 주문 목록 → 주문 상세 → (5번 중 1번) 환불 요청 | 3.2 (평균) |

#### 비율 근거
- **C 20%:** 결제 README의 "결제 20%" 가정과 같다. 그래서 C의 분당 50회는 새 기준 결제 목표 "세션 분당 50개"(8-2)와 같은 값이 된다
- **채팅 사용(B + C) 50%:** 채팅 견적이 이 서비스의 핵심 기능이라 둘러보기 다음으로 많다고 본다. 견적을 받은 사람(50%) 중 40%가 구매한다(20%)
- **A 40%:** 이커머스에서 가장 많은 행동은 상품 조회라는 일반적인 전환 흐름을 따른다
- **D 10%:** 주문한 사람이 다음 방문에서 배송 상태를 보는 경우
- 비율은 실제 데이터가 아니다. 결과서에 "가정"이라고 쓴다

#### 메시지를 의도별로 섞는 이유
로컬 새 기준 결과는 fake LLM이 모든 메시지를 견적 요청으로 처리했다. 이번에는 fake가 문장 단어로 의도를 정해(5-2), 의도마다 LLM 호출과 서버 작업이 달라진다.

| 의도 (`MenuPlanIntent`) | LLM 작업 (`LlmOperation`) | 서버 작업 |
|---|---|---|
| 견적 요청 `SHOPPING_REQUEST` | 메뉴 계획 → 견적 안내 | 새 견적 발급 (DB, Redis) |
| 견적 수정 `QUOTE_EDIT` | 메뉴 계획 → 견적 수정 계획 → 견적 안내 | 견적 락, 견적 수정 |
| 리뷰 질문 `LOOKUP_QUESTION` | 메뉴 계획 → 조회 답변 (도구 호출 왕복 포함) | 리뷰 조회 (DB) |
| 일반 질문 `GENERAL_QUESTION` | 메뉴 계획 → 일반 답변 | 메시지 저장만 |

메시지 문장. fake 의도 단어(빼·리뷰·보관)가 들어 있다 (5-2)

| 흐름 | 순서 | 문장 | 기대 의도 | 응답 형식 (k6 check, `kind:format`) |
|---|---|---|---|---|
| B | 1 | 김치볶음밥 재료 준비해 줘 | 견적 요청 | `QUOTE_CARD`, 상품 1개 이상 |
| B | 2 | 4인분으로 해 줘 | 견적 요청 (인분 변경은 새 견적, `MenuPlanIntent` 주석) | `QUOTE_CARD`, 상품 1개 이상 |
| B | 3 | 계란은 빼 줘 | 견적 수정 | 글 답변 (fake 견적 수정은 카드 대신 되묻는다, 5-2) |
| B | 4 | 이 김치 리뷰 어때? | 리뷰 질문 | 글 답변 |
| B | 5 | 남은 김치볶음밥은 어떻게 보관해? | 일반 질문 | 글 답변 |
| C | 1 | 된장찌개 재료 준비해 줘 | 견적 요청 | B 1과 같음 |
| C | 2 | 2인분으로 해 줘 | 견적 요청 | B 2와 같음 |
| C | 3 | 대파는 빼 줘 | 견적 수정 | B 3과 같음 |

- fake는 문장 단어로 의도를 정하므로 응답 내용(메뉴, 인분, 대상 품목이 빠졌는지)과 실제 의도 분류 정확도는 이번 테스트로 보지 않는다. 형식이 다르면 서버가 다른 길로 처리했거나 스크립트 문제다
- 서버가 실제로 처리한 의도별 건수는 `zelo_chat_reply_seconds`의 `intent` 태그로 센다. k6가 보낸 문장별 건수와 맞는지 결과서에 적는다

- 문장은 여러 메뉴(김치볶음밥, 된장찌개, 카레 등)로 돌려 쓴다. 같은 문장만 보내면 상품 후보가 늘 같아 DB 캐시가 실제보다 잘 맞는다
- 리뷰 질문의 상품은 리뷰 시드(`ReviewSeedLoader`)가 있는 상품으로 고른다

#### 도메인 기준선과의 차이
1단계 도메인 기준선은 "그 도메인을 쓰는 사용자 전부가 피크에 몰린다"는 값으로, 그 도메인 요청만 보내서 잰다.

| 도메인 | 기준선 (×1) | 통합 ×1에서 같은 요청 | 차이 |
|---|---|---|---|
| 채팅 | 분당 125세션 (견적을 받는 B + C 50%), 메시지 10.4 RPS | B 75 + C 50 = 분당 125세션, 메시지 8.75 RPS | 세션 수는 같다. 기준선은 세션마다 메시지 5개, 통합은 B 5개·C 3개라 메시지가 적다 |
| 상품 | 41.7 RPS (사용자 1만 명 전부가 10번 부른다고 봄, 상품 README) | A 100 × 9 ÷ 60 = 15 RPS | 기준선이 더 나쁜 경우다 |
| 주문·결제 | 분당 50세션 (구매 20%) | C 분당 50회 | 같다 |
| 환불 | 분당 5회 (환불 2%) | D 25회 중 1/5 = 분당 5회 | 같다 |

### 3-3. ×1에서 예상 트래픽

| 항목 | 계산 | 값 |
|---|---|---|
| 전체 요청 | (100 × 9 + 75 × 8 + 50 × 11 + 25 × 3.2) ÷ 60 | **약 35.5 RPS** |
| 채팅 메시지 | (75 × 5 + 50 × 3) ÷ 60 | **약 8.75 RPS** (분당 525개) |
| LLM 호출 | 5-3 참고 | **분당 약 1,175회** (fake 호출) |
| 주문 생성 | 50 ÷ 60 | 약 0.83 RPS |
| 결제 요청 (결제수단 조회 + 결제) | 50 × 2 ÷ 60 | 약 1.67 RPS (새 기준 결제 목표 약 1.9 RPS와 비슷) |
| 로그인 | (75 + 50 + 25) ÷ 60 | 약 2.5 RPS |

#### 동시 VU 예상 (리틀의 법칙: VU = 초당 시작 수 × 흐름 하나의 시간)

| 흐름 | 흐름 하나의 시간 (예상) | VU |
|---|---|---|
| A | 요청 9개 + 생각 시간 평균 2초 × 8 ≈ 17초 | 100/60 × 17 ≈ 28 |
| B | 메시지 5개 × 약 12초 + 생각 시간 ≈ 75초 | 75/60 × 75 ≈ 94 |
| C | 메시지 3개 약 40초 + 나머지 약 15초 ≈ 55초 | 50/60 × 55 ≈ 46 |
| D | 약 6초 (생각 시간 포함) | 25/60 × 6 ≈ 2.5 |
| 합계 | | **약 170** |

- 메시지 시간 12초는 **가정**이다. 5-1의 fake 지연으로는 메시지 하나가 약 3.5\~5.7초(평균)라 이보다 짧다. 사전 확인 스모크로 재서 바꾼다
- 채팅 메시지가 Tomcat 스레드를 잡는 수 = 8.75 RPS × 12초 ≈ 105개로, 200개의 절반쯤이다 (4-1-3 기준 140개 안쪽)
- 이 값은 k6 VU 설정(`preAllocatedVUs`)의 근거로만 쓴다. 트래픽은 VU 수가 아니라 분당 방문 수로 정한다(`constant-arrival-rate`). 서버가 느려져도 요청이 줄지 않아야 실제 상황과 같기 때문이다

### 3-4. 생각 시간
- 통합 테스트에서는 요청 사이에 1\~3초를 무작위로 쉰다 (`sleep(1 + Math.random() * 2)`). 채팅 메시지 사이에도 같은 값을 넣는다
- 근거: 실제 사용자는 화면을 보고 다음 행동을 한다. 쉬는 시간이 없으면 한 사용자가 서버를 연달아 두드려 동시 세션 수, 토큰 사용 시간, Redis 키 수명이 실제와 달라진다
- 서버에 들어가는 RPS는 바뀌지 않고 동시 VU만 늘어난다 (3-3 표)
- 도메인 기준선은 로컬과 비교하려고 생각 시간 없이 그대로 둔다

### 3-5. 사용자 번호대와 로그인 방식
흐름마다 필요한 시드 데이터(채팅 기록, 결제수단, 결제 완료 주문)가 사용자 번호대별로 들어가 있으므로, 흐름마다 번호대는 겹치지 않게 쓴다. 겹치면 채팅 메시지 제한(1분 10건)이나 주문 상태 때문에 다른 흐름이 실패한다.
로그인 방식은 **B·C·D 모두 이메일 70%, 소셜 fake 30%로 같게 둔다.** 시드 사용자 전체 비율(이메일 21,000명, 소셜 9,000명)과 같다.

| 흐름 | 사용자 | 이메일 (70%) | 소셜 fake (30%) | 이 번호대를 쓰는 이유 |
|---|---|---|---|---|
| A | 없음 | | | 상품 API는 인증이 필요 없다 |
| B | 5,001\~15,000 (10,000명) | 7,000명 | 3,000명 | 채팅 시드(`LoadTestChatSeedLoader`)의 방 기록이 있는 사용자 |
| C | 20,001\~25,000 (5,000명) | 3,500명 | 1,500명 | 결제 시드(`LoadTestPaymentSeedLoader`)가 결제수단과 배송지를 넣은 사용자 |
| D | 25,001\~27,000 (2,000명) | 1,400명 | 600명 | 환불 시드(`LoadTestRefundSeedLoader`)가 결제 완료 주문을 넣은 사용자 |

- **규칙:** 사용자 번호의 끝자리가 1\~7이면 이메일, 8·9·0이면 소셜 fake다. 번호대가 모두 끝자리 1에서 시작하고 크기가 10의 배수라, 어느 흐름이든 정확히 7:3이 된다
  - 이메일: `POST /api/users/login` (`load{id}@test.com`, 공통 비밀번호)
  - 소셜 fake: `POST /api/auth/social/google/login` (`fake-load-{id}`)
- k6는 흐름 안에서 사용자를 번호 순서대로 돌려 쓴다. 연속한 10명마다 7:3이라 실행 중 어느 구간에서도 비율이 거의 같다
- **비율을 같게 두는 이유:** 이메일 로그인은 BCrypt 해시로 앱 CPU를 쓰고, 소셜 fake는 900ms 지연(`zelo.social.fake-latency-ms`) 동안 요청 스레드를 잡는다. 흐름마다 비율이 다르면 흐름별 응답 시간에 로그인 방식 차이가 섞여, 흐름끼리 비교할 수 없다
- **C는 결제 시드를 결제 대기 주문 없이 넣고 쓴다.** 결제 시드는 기본으로 20,001\~25,000번 5,000명에게 결제 대기 주문을 20건씩(총 10만 건) 넣는데, 결제 대기 주문이 있으면 새 주문이 409(`ORDER_004`, `OrderService.validateNoPendingOrder`)다. 2026-11-06 로컬 통합 사전 확인에서 C의 주문 생성 11건이 모두 이 오류였다
  - 결제 담당이 설정 `zelo.seed.load-test.payment-order-count`(기본 100,000)를 넣었다. **0이면 결제수단만 넣고 결제 대기 주문은 넣지 않는다.** 통합 테스트는 이 값을 0으로 앱을 띄운다 (6-2)
  - 그러면 20,001\~25,000번 5,000명 모두 C에 쓸 수 있다. 통합 부하 25분에 C 방문은 약 1,150회라 한 번 실행에서 같은 사용자를 다시 쓰지 않는다
  - 결제 시드는 앱을 켤 때마다 지우고 새로 넣으므로, 켤 때 설정만 바꾸면 결제 도메인 테스트(기본값 10만 건)와 섞이지 않는다
  - 시드가 지우는 것은 시드 주문뿐이다. C가 만든 주문은 남는다. 결제까지 성공한 주문은 결제 완료라 막지 않지만, 결제 전에 끊긴 방문의 결제 대기 주문은 그 사용자의 다음 주문을 막는다. 같은 DB로 통합을 다시 돌리면 `-e PURCHASE_FIRST_USER`로 앞 실행이 쓰지 않은 번호부터 쓰거나, DB를 시드 상태로 되돌린다
- **C가 사는 상품의 재고를 늘리고 시작한다.** fake 메뉴 계획은 문장과 관계없이 늘 같은 재료 4개(김치 400g, 밥 800g, 계란 4개, 대파 100g, `FakeLlmGateway.planMenu`)를 돌려줘서, 모든 구매가 같은 상품에 몰린다. 시드 재고는 상품당 20~199개라 통합 부하(C 약 1,150건)에서 금방 바닥나 주문이 `PRODUCT_002`(재고 부족)로 실패한다
  - 2026-11-06 로컬 통합 사전 확인에서 "알뜰 알뜰 계란 6구"(재고 0), "소포장 큰 즉석밥 300g"(재고 1) 때문에 구매 10건 중 2건이 이 오류였다. 재고를 늘린 뒤 다시 돌려 11건 모두 결제 완료까지 갔다
  - 통합 테스트는 앱을 **`zelo.seed.load-test.extra-stock=100000`**으로 띄운다 (`LoadTestExtraStockSeedLoader`). 앱을 켤 때 그 4개 재료 상품의 재고를 이 값으로 맞춘다(가용 재고는 잡힌 재고를 뺀 값). 더하지 않고 맞추므로 서버가 여러 대이거나 재시작해도 재고가 쌓이지 않는다. 설정이 없으면(기본 0) 아무것도 하지 않아 다른 도메인 테스트에는 영향이 없다
  - 시드에서 재고 0으로 넣은 상품(검색의 `inStock` 조건용)은 품절 그대로 둔다
  - 그래서 통합 결과의 주문은 "같은 재료에 몰리지만 재고는 충분한" 조건이다. 인기 상품 재고가 바닥나는 상황은 8-2 주문 ②로 따로 잰다

#### 먼저 바꿀 것 (통합 테스트 전 로컬 작업)
지금 시드는 번호대로 나눈다 (`LoadTestUserSeedLoader`: 1\~21,000 이메일, 21,001\~30,000 소셜). 이대로면 B는 모두 이메일, C는 이메일 1,000명·소셜 4,000명, D는 모두 소셜이라 위 비율을 만들 수 없다.

1. `LoadTestUserSeedLoader`의 이메일·소셜 구분(`isEmailUser`, 소셜 계정을 넣을 번호 목록)을 끝자리 규칙으로 바꾼다. 전체 인원과 비율(70:30)은 그대로다
2. 이 시드는 1\~30,000번에 사용자가 하나라도 있으면 건너뛰므로, 이미 시드가 있는 DB에서는 사용자 시드를 지우고 다시 넣는다
3. 번호대로 로그인 방식을 고르던 k6 스크립트를 같은 규칙으로 바꾼다
   - `payment/payment-session.js`, `refund/refund-session.js` (`EMAIL_USER_MAX = 21000`)
   - `auth/social-login-*.js` (21,001번부터 차례로 소셜 로그인)
   - 이메일 로그인만 하는 스크립트 (채팅, 견적, 주문, 인증): 소셜 번호를 이메일로 로그인하면 실패하므로 같은 규칙을 쓴다
4. 바꾼 뒤 재는 도메인 결과는 예전 결과와 로그인 비율이 다르다. 결과서 "조건"에 적는다

## 4. 판정 기준

통합 테스트(2·3·4단계)와 도메인별 테스트(1단계)의 기준을 나눠 적는다.
모든 테스트를 fake LLM(실측 지연, 5-1)으로 하므로, AI 묶음 시간은 fake 기준이다.

### 4-1. 통합 테스트 판정·통과 기준 (2·3·4단계)

#### 4-1-1. API별 응답 시간

| 묶음 | API | p95 기준 | 근거 |
|---|---|---|---|
| 입력 중 응답 | 자동완성 | 200ms | 글자를 칠 때마다 부른다. Nielsen의 응답 시간 기준에서 0.1초가 "바로 반응", 1초가 "흐름이 끊기지 않음"이다. 그 사이에서 엄격한 쪽 |
| 조회 | 상품 목록·검색·상세, 인기 상품, 인기 검색어, 카테고리, 방 목록, 메시지 목록, 주문 목록·상세, 배송지, 결제수단 | 500ms | 1초 기준의 절반. 로컬에서 방 목록 p95 0.01초, 결제수단 조회 수십 ms로 여유가 크다 |
| 인증 | 이메일 로그인 (`loginType:email`) | 500ms | BCrypt 해시가 CPU를 쓴다. 로컬 부하 p95 0.19초 |
| | 소셜 로그인 (`loginType:social`) | 2,000ms | fake가 외부 응답 대기를 평균 900ms ±50%(최대 약 1.35초)로 흉내 낸다. 인증 README의 소셜 로그인 부하 기준과 같다 (로컬 부하 p95 1.33초) |
| 쓰기 | 구매 확인, 주문 생성, 환불 요청 | 1초 | 주문 생성은 같은 사용자의 주문 생성을 막는 Redisson 분산락(대기 한도 3초) 안에서 상품마다 재고 행을 DB 행 잠금으로 잡고 차감한다. 분산락 대기 한도가 3초라 그 안에서 충분히 끝나야 한다 |
| 결제 | 등록 카드 결제 | 1.5초 | 포트원 빌링키 결제 실측 p95 1.01초 (README) + 서버 처리 |
| AI | 채팅 메시지 전체 | **20초 (잠정)** | 메시지 시간 예산(`time-budget.total`) 30초보다 충분히 짧아야 한다. fake 지연(5-1)으로는 메시지 하나의 LLM 시간이 가장 길어야 약 7.7초(메뉴 계획 3.6초 + 리뷰 답변 4.1초)라, 이 기준을 넘으면 서버 쪽 대기가 원인이다 |

- AI 묶음은 의도별(`intent` 태그)로도 따로 적는다. 견적 요청과 일반 질문은 견적 수정보다 짧아야 한다
- 서버 처리 시간(메시지 시간에서 LLM 시간을 뺀 값)은 따로 계산한다 (7장). LLM 대기와 우리 서버가 느린 것을 나눠 보기 위해서다

#### 4-1-2. 실패율

| 대상 | 기준 | 비고 |
|---|---|---|
| 전체 요청 | `http_req_failed` < 1%, 상태 코드 check(`checks{kind:status}`) > 99% | 5xx와 예상하지 못한 4xx. 기대와 다른 2xx(201 대신 200, 토큰 없는 로그인 200)는 `http_req_failed`에 안 잡혀서 상태 코드 check로 본다 |
| 결제 요청 | < 0.1% (`http_req_failed{kind:payment}`, `payment_failed`) | 돈이 걸린 요청이라 더 엄격하게. 결제 API는 실패·취소·확인 대기도 200으로 돌려줘서(`PaymentController.payWithPaymentMethod`), 응답의 `data.status`가 `PAID`가 아니면 실패로 센다(`payment_failed`) |
| 채팅 FALLBACK | < 1% | 503(AI_008), 504(AI_002)는 실패 안내라는 정상 응답이지만, 부하 테스트에서 1%를 넘으면 문제로 본다. fake에는 429가 없으므로, 생기면 시간 예산 초과나 서버 쪽 원인이다 (7장 지표로 나눈다) |
| 견적 안내 생략 (DEGRADED) | < 5% | 카드는 저장되지만 안내가 고정 문구다. 지표 `zelo.chat.explain.degraded` (`BusinessMetric.CHAT_EXPLAIN_DEGRADED`) |
| 응답 형식이 기대와 다름 | < 1% | fake는 문장별 의도를 정해 주므로 형식(카드·글 답변)이 바뀌면 서버나 스크립트 문제다 (3-2) |
| 구매 완료율 (C) | 사전 확인에서 정한 값 이상 (`visit_completed{journey:purchase}`, 스크립트 기본 99%, `-e PURCHASE_COMPLETION_RATE`로 바꾼다) | 로그인부터 주문 상세까지 끝까지 간 방문의 비율이다. HTTP는 성공했지만 업무 상태가 틀려 끊긴 방문도 실패로 센다. 어디서 끊겼는지는 단계별 도달 건수(9-2 C)로 본다. 낮으면 주문·결제 요청이 목표보다 적게 들어간 것이라 주문·결제 결과를 "목표 부하를 처리했다"로 쓰지 않는다 |

#### 4-1-3. 서버 상태

| 항목 | 기준 | 이유 |
|---|---|---|
| Hikari 대기 (`hikaricp_connections_pending`) | 대부분 0, 커넥션 얻는 시간 p95 < 100ms | 대기가 생기면 모든 도메인이 같이 느려진다 |
| Tomcat 바쁜 스레드 | 최대의 70% 미만 (200개 중 140) | 70%를 넘으면 조금만 늘어도 꽉 찬다 |
| 앱 CPU | 평균 70% 미만 | 같은 이유 |
| k6 놓친 방문 (`dropped_iterations`) | 0 | 0이 아니면 k6가 목표만큼 보내지 못한 것이라 결과를 믿을 수 없다 |
| 부하 발생기 CPU | 80% 미만 | 넘으면 측정값에 k6 지연이 섞인다. 로컬에서는 같은 노트북이라 99.8%까지 찼다 |
| 데이터 정합성 | 재고 음수 0, 결제 완료 건수 = k6 결제 성공 수, 중복 주문 0 | 빠르지만 틀리면 통과가 아니다 |

#### 4-1-4. 목표 여유
- **부하 통과:** 통합 ×1에서 위 기준을 모두 지킨다
- **스트레스 목표:** SLO를 지키는 최대 배수가 통합 ×1.5 이상 (채팅 새 기준 결과서의 여유 기준과 같다)
- 근거: 목표에 안전계수 1.5를 이미 넣었다. 새 기준은 예전 기준의 10배라, 예전처럼 ×3을 요구하면 예전 기준의 30배를 버텨야 한다. 로컬 fake에서 채팅 한계가 목표의 약 2배(Tomcat 200)였다. ×1.5에서 못 버티면 4단계에서 고칠 대상으로 삼는다
- 모든 테스트가 fake LLM이라 이 배수는 "fake LLM(실측 지연) 기준"이다. 실제 OpenAI로 같은 트래픽을 보내면 한도(5-0)에 먼저 막힌다. 배수별 분당 토큰(분당 호출 × 약 2,320)을 계산해 결과서에 같이 적는다

## 5. LLM 조건

### 5-0. 실제 OpenAI를 쓰지 않는 이유: 계정 한도
2026-11-06 로컬에서 실제 OpenAI(`gpt-6-luna`)로 채팅 도메인 부하(분당 125세션, 데우기 2분 + 측정 5분)를 돌렸다.

| 항목 | 값 |
|---|---|
| 목표 속도에서의 LLM 사용 | 분당 시도 약 1,375회, 토큰 약 320만 (호출 1회 약 2,320토큰) |
| 429 (`AI_003`) | 시작 약 3.5분 뒤 16번, 약 2분 뒤 14번 |
| 서킷 | 두 번 열림 (각 약 36초). 그동안 메시지 387건이 LLM을 부르지 않고 실패 안내(`AI_008`, 503) |
| k6 결과 | 실패율 9.15% (기준 1%), 기본 check 90.84% |
| 우리 서버 | Tomcat 바쁜 스레드 평균 29·최대 56 (200개 중), DB 커넥션 대기 0 |

- 같은 키로 OpenAI를 1번 불러 응답 헤더를 보니 `x-ratelimit-limit-requests: 5000`, **`x-ratelimit-limit-tokens: 2000000`**이었다. 2026-11-05에 적은 TPM 2,000만은 이 키·모델에 적용되는 값이 아니었다
- 분당 토큰 한도 200만은 1분 단위로 다시 채워진다. 목표 속도에서는 채워지는 양보다 분당 약 120만이 더 빠져나가, 시작 뒤 1분 반 남짓 지나 처음 429가 났다
- 목표 트래픽은 이 한도의 약 160%(계획서 기준 1.2배 여유를 넣으면 약 190%)다. 한도 안에서 실제로 보낼 수 있는 것은 분당 약 65세션(목표의 약 52%)이다
- 그래서 **모든 테스트를 fake LLM으로 하고, 이 실행에서 잰 작업별 LLM 시간을 fake 지연으로 넣는다** (5-1). 실제 OpenAI 호출과 비용은 0이다
- 잃는 것: 실제 OpenAI의 지연 흔들림, 의도 분류 정확도, AI 오류율(응답 검증 실패), 429와 서킷 열림을 부하 중에 볼 수 없다. 결과서에 "fake LLM(실측 지연) 기준"이라고 적는다
- **운영 용량 문제로 따로 알린다.** 운영 키도 같은 한도라면, 피크 목표에서 실제 서비스가 429와 서킷 열림을 겪는다. 한도 상향(사용 등급, 프로젝트 한도) 또는 호출당 토큰 줄이기(메뉴 계획 프롬프트 약 2,750토큰)를 팀에서 정한다
- 원본(k6 요약·CSV, 서버 지표 CSV, 시작·끝 Prometheus)은 결과서에 넣을 때 `docs/load-test/results/chat/`에 함께 남긴다

### 5-1. fake 지연 (작업별 실측)
위 실행의 `zelo_llm_attempt_seconds`(성공한 시도만, 시작·끝 Prometheus 히스토그램 차이)에서 뽑았다. `FakeLlmGateway`는 범위 안에서 고르게 고르므로, 범위를 **[실측 p5, 평균이 실측 평균과 같아지는 값]**으로 정했다.

| 작업 (`LlmOperation`) | 시도 수 | 실측 평균 | 실측 p50 | 실측 p95 | fake 범위 | fake 평균 | fake p95 |
|---|---|---|---|---|---|---|---|
| 메뉴 계획 `MENU_PLAN` | 2,797 | 2.36초 | 1.84초 | 5.85초 | 1.1\~3.6초 | 2.35초 | 3.48초 |
| 견적 안내 `QUOTE_EXPLAIN` | 1,694 | 1.42초 | 1.32초 | 2.15초 | 1.0\~1.8초 | 1.40초 | 1.76초 |
| 견적 수정 계획 `QUOTE_EDIT_PLAN` | 549 | 1.63초 | 1.46초 | 2.35초 | 1.1\~2.2초 | 1.65초 | 2.15초 |
| 리뷰 답변 `LOOKUP_ANSWER` | 525 | 3.35초 | 3.11초 | 5.26초 | 2.6\~4.1초 | 3.35초 | 4.02초 |
| 일반 답변 `CHAT_ANSWER` | 512 | 1.87초 | 1.77초 | 2.71초 | 1.4\~2.3초 | 1.85초 | 2.25초 |

```
zelo.llm.fake.operation-delays=MENU_PLAN:1100ms-3600ms,QUOTE_EXPLAIN:1000ms-1800ms,QUOTE_EDIT_PLAN:1100ms-2200ms,LOOKUP_ANSWER:2600ms-4100ms,CHAT_ANSWER:1400ms-2300ms
```

- **평균을 맞춘 이유:** 동시에 진행 중인 요청 수(Tomcat 스레드 점유)는 평균 처리 시간으로 정해진다(리틀의 법칙). 부하·스트레스의 한계를 정하는 값이다
- **p95는 실측보다 짧다.** 실측 분포는 꼬리가 길어(특히 메뉴 계획 p95 5.85초) 균등 분포로는 평균과 p95를 함께 맞출 수 없다. 그래서 fake의 메시지 p95는 실제 OpenAI보다 낮게 나온다. 결과서의 p95는 "fake 기준"으로 읽는다
- 측정 조건: 로컬 PC 한 대, 429 전후 구간 포함. AWS에서 OpenAI까지의 지연과 다를 수 있다
- fake는 재시도를 만들지 않는다. 실측에서는 메뉴 계획 첫 시도의 약 1.6%(46/2,843)가 응답 검증에 걸려 재시도했다(그중 1건만 사용자에게 실패)

### 5-2. fake 의도와 흉내 내지 못하는 것
- 의도는 문장 단어로 정한다: `zelo.llm.fake.intent-keywords=QUOTE_EDIT:빼,LOOKUP_QUESTION:리뷰,GENERAL_QUESTION:보관`. 맞는 단어가 없는 문장(견적 요청·인분 변경)은 `zelo.llm.fake.plan-intent=SHOPPING_REQUEST`
- 흉내 내지 못하는 것
  - fake 견적 수정 계획은 현재 견적을 보지 않아 수정하지 않고 "어떤 상품을 바꿀까요?"로 되묻는다(카드 없음). 견적 락·수정 작업이 빠진다
  - fake 리뷰 답변은 조회 도구(DB)를 부르지 않는다. 리뷰 조회 쿼리가 빠진다
  - 보강하지 못하면 결과서에 "견적 수정·리뷰 조회의 서버 작업 빠짐"이라고 적는다

### 5-3. 흐름별 LLM 호출 수 (fake 호출)

| 흐름 | 메시지 | 호출 | 합계 |
|---|---|---|---|
| B | 견적 요청 2 + 인분 변경 2 + 견적 수정 2 + 리뷰 질문 2 + 일반 질문 2 | | **10** |
| C | 견적 요청 2 + 인분 변경 2 + 견적 수정 2 | | **6** |

- fake 견적 수정은 메뉴 계획 → 견적 수정 계획 뒤 되묻기로 끝나 견적 안내를 부르지 않는다 (실제 OpenAI에서는 3번)
- ×1 분당 호출: 통합 75 × 10 + 50 × 6 = **1,050**, 채팅 기준선 125 × 10 = **1,250**
- 참고로 실제 OpenAI였다면 호출 1회 약 2,320토큰이라, 채팅 기준선만으로도 분당 약 320만 토큰(견적 수정 3번 기준)으로 한도(5-0)를 넘는다

#### AWS에서 fake 설정 넣기
AWS의 앱은 실행 인자 없이 뜨고(`terraform/templates/zelo-deploy.sh.tftpl`), 설정은 시작할 때 SSM `/zelo/dev/` 아래에서 읽는다. 파라미터 이름이 곧 프로퍼티 이름이고, SSM 값이 프로필 파일보다 우선한다. 그래서 아래 값을 **SSM에 넣고 앱을 다시 띄운다** (`docker restart zelo`). 프로필은 Terraform `spring_profile` 기본값 `performance`를 쓴다.

| SSM 파라미터 | 값 |
|---|---|
| `LLM_MODE` | `fake` (Terraform 초기값) |
| `zelo.llm.fake.mode` | `DELAY` |
| `zelo.llm.fake.plan-intent` | `SHOPPING_REQUEST` |
| `zelo.llm.fake.operation-delays` | 5-1의 값 |
| `zelo.llm.fake.intent-keywords` | `QUOTE_EDIT:빼,LOOKUP_QUESTION:리뷰,GENERAL_QUESTION:보관` |
| `zelo.seed.load-test.payment-order-count` | 통합 테스트만 `0` (결제 시드가 결제 대기 주문 없이 결제수단만 넣는다, 3-5). **통합이 끝나면 지운다.** 남아 있으면 결제 도메인 테스트 때 결제 대기 주문 10만 건이 들어가지 않는다 |

- 포트원 fake 지연은 `performance` 프로필에 들어 있어 넣지 않는다 (#438)
- 로컬은 같은 값을 실행 인자로 준다 (`--zelo.seed.load-test.payment-order-count=0` 등, `load-test/integrated/integrated-load.js` 주석)
- fake 설정을 넣지 않으면 기본값(`mode=NORMAL`: 지연 없음, `plan-intent=GENERAL_QUESTION`: 모든 메시지가 일반 질문)으로 떠서 측정이 의미가 없다
- Terraform이 만드는 파라미터가 아니라서 CLI로 넣는다 (예: `aws ssm put-parameter --name /zelo/dev/zelo.llm.fake.mode --type String --value DELAY --overwrite`)
- 확인: 스모크 뒤 `zelo_llm_tokens_total`이 늘지 않고(fake는 토큰을 0으로 남긴다), `zelo_llm_attempt_seconds`가 작업별로 설정한 범위 안이다
- k6 명령은 모두 `-e BASE_URL=`(ALB 주소)을 주고, `record-metrics.sh`는 `METRICS_URL=`(앱의 9292 주소)을 준다

## 7. 관측 지표

로컬에서는 `record-metrics.sh`로 5초마다 CSV를 남겼다. AWS에서는 Prometheus가 actuator(9292)를 수집하고 Grafana로 본다. 같은 스크립트를 k6 EC2에서 함께 돌려 CSV도 남긴다(결과서에 넣기 쉽다).

| 층 | 지표 | 보는 이유 |
|---|---|---|
| k6 | API별(`name` 태그) p50·p95·p99, 실패율, `dropped_iterations`, 흐름별(`journey`), 의도별(`intent`) | 판정 기준 |
| 앱 HTTP | `http_server_requests_seconds` (uri별) | k6와 서버 시간의 차이로 네트워크, ALB 대기를 구분 |
| Tomcat | `tomcat_threads_busy_threads` | 스레드 포화. LLM(fake 지연)을 기다리는 동안 채팅 요청이 스레드를 잡는다 |
| Hikari | `hikaricp_connections_active`·`pending`, `acquire`·`usage` 히스토그램, `timeout_total` | DB 커넥션 포화. **`_max`는 최근 2\~3분 값이라 전체 최대로 쓰지 않는다** (로컬 결과서 5장) |
| LLM | `zelo_llm_call_seconds`·`zelo_llm_attempt_seconds` (operation, outcome), `zelo_llm_execution_started_total`, `zelo_llm_time_budget_exceeded_total`, `resilience4j_circuitbreaker_state` | fake 지연이 설정대로 나오는지(5-1), 시간 예산, 서킷 |
| 채팅 | `zelo_chat_reply_seconds` (intent, outcome), `zelo_chat_fallback_total` (code), `zelo.chat.explain.degraded`, `zelo.chat.quote.busy`, `zelo.chat.rate.limited` | 의도별 처리 시간, FALLBACK 원인, 견적 락 대기 |
| 업무 | `zelo_api_error_total{code}`, `zelo_payment_result_total{status}` | 실패 원인 |
| 인프라 | CloudWatch: EC2 CPU, ALB `TargetResponseTime`·`HTTPCode_Target_5XX`, RDS `CPUUtilization`·`DatabaseConnections`, NAT 게이트웨이 처리량 | 앱 밖의 병목 |
| DB 쿼리 | RDS Performance Insights (상위 SQL, 대기 이벤트) | 느린 쿼리와 락 대기를 SQL 단위로 찾는다 |

### 7-1. 분석 규칙 (로컬에서 틀렸던 것)
- 단계별 집계는 k6 CSV의 `timestamp`(요청이 **끝난** 시각)가 아니라 **보낸 시각 = timestamp − duration**으로 나눈다. 끝난 시각으로 나눴을 때 스트레스 ×3 p95가 34.2초가 아니라 23.7초로 잘못 나왔다
- 시작과 끝에 `/actuator/prometheus` 전체를 파일로 저장한다. 누적 히스토그램 차이로 테스트 동안의 정확한 건수를 계산할 수 있다
- **서버 처리 시간 = 채팅 메시지 시간 − 그 메시지의 LLM 시간.** 메시지 단위로는 로그의 traceId로 맞추고, 전체로는 `zelo_chat_reply_seconds` 합계 − `zelo_llm_call_seconds` 합계를 메시지 수로 나눠 평균을 본다

### 7-2. 원인까지 좁히는 방법
위 지표로 **어떤 기능이 느려졌는지, 어떤 자원이 찼는지**는 상당 부분 알 수 있다. 하지만 아래 두 문장은 증거 수준이 다르다.

- "주문 생성이 느리고 DB 대기가 많았다."
- "주문 생성 중 특정 재고 조회가 행 잠금을 기다리면서 느려졌다."

두 번째까지 말하려면 아래 단계가 끊기지 않고 이어져야 한다. 결과서의 원인 문장은 몇 단계까지 확인했는지 함께 적는다.

| 확인 단계 | 필요한 기록 | 이 계획에서 쓰는 것 |
|---|---|---|
| 어떤 API가 느린가 | API별 응답 시간·실패율 | k6 `name` 태그, `http_server_requests_seconds` (7-1) |
| 어떤 요청을 조사할까 | 느린 요청의 `X-Trace-Id` | 응답 헤더 `X-Trace-Id`(`TraceIdResponseFilter`). k6에서 기준을 넘은 요청과 실패한 요청의 traceId를 VU마다 처음 몇 건만 로그로 남긴다 |
| 요청 내부 어디가 느린가 | 락 대기·재고 조회·외부 호출·저장 구간 시간 | 채팅은 LLM 시간(`zelo_llm_call_seconds`)과 서버 처리 시간이 이미 있다. 나머지는 아래 "추가할 내부 측정" |
| 왜 그 구간이 느린가 | DB 대기 이벤트·SQL·로그 | RDS Performance Insights(대기 이벤트, 상위 SQL), traceId로 모은 그 요청의 로그 |
| 정말 그 원인인가 | 한 조건만 바꾼 비교 실험 | 아래 "원인 확인 실험", 4단계 전·후 비교 (11-2) |

#### 추가할 내부 측정 (많지 않다)
지금 지표로 나뉘지 않는 구간만 시간을 잰다. 이름은 `BusinessMetric` enum에 추가하고, 태그는 결과·에러 코드처럼 값이 정해진 것만 쓴다 (팀 지표 기준). 각 도메인 담당이 넣는다.

| 도메인 | 잴 구간 |
|---|---|
| 주문 | 분산락 대기(`LockKey.createOrder`), 재고 조회·잠금(`findInventoryByProduct_Id`), 주문 저장 |
| 결제·환불 | 락 대기, 외부 호출(포트원, fake 지연 포함), 결과 저장 |
| 채팅 | 기존 지표로 나뉘지 않는 구간: 견적 수정(견적 락 대기 포함), 리뷰 도구 조회 |

#### 원인 확인 실험
지표가 같이 움직인다는 것만으로는 원인이라고 말할 수 없다. 의심하는 조건 하나만 바꾸고 나머지는 고정한 실험으로 확인한다.

- 예: **채팅이 다른 기능을 느리게 하는지** 확인하려면 상품 조회량은 고정하고 채팅량만 늘린다. 상품 조회 지연이 함께 늘고, 요청 스레드 대기(Tomcat 바쁜 스레드가 최대에 닿음)가 늘어나는 것이 확인되면 기능 간 영향에 대한 설명이 훨씬 강해진다
- 실험은 3단계 스트레스와 같은 fake LLM 환경에서 한다. LLM 변동이 없어 바꾼 조건의 효과만 남는다

## 8. 1단계: 도메인별 부하·스트레스

### 8-1. 공통 방법
1. 사전 확인 (VU 1\~3, 1\~2분): 기준 응답 시간을 잰다
2. 부하: 도메인 목표 ×1을 10분 (채팅은 로컬 새 기준 결과와 같게 데우기 2분 + 측정 5분)
3. 스트레스: ×1부터 무너질 때까지 단계적으로 올린다. 단계마다 3분 이상 유지 (로컬 채팅은 80초라 단계 사이에 섞이는 구간이 컸다)
4. 결과는 `docs/load-test/results/<도메인>/aws-...`에 남기고, 로컬 결과와 나란히 표로 비교한다

### 8-2. 도메인별 계획

| 도메인 | 로컬 상태 | 측정할 API·흐름 | 목표 ×1 | 하는 테스트 | 찾을 결점 (가설) |

| 주문 | 새 기준 3종·한계 완료 (로컬, 분당 100세션 = 이 표 목표의 2배): 주문 요청 p95 약 18ms, ×100(501 RPS)까지 안정, 한계는 못 찾음. 스트레스 ②(같은 인기 상품 몰림)는 아직 안 함 | 구매 확인 → 주문 생성 | 분당 50세션 (1만 × 20% × 3회 ÷ 3,600초 × 1.5 = 2.5 RPS) | 부하, 스트레스 | 주문 생성에는 잠금이 두 가지다. 둘을 나눠 본다. ① **Redisson 분산락** `LockKey.createOrder(userId)`: 같은 사용자의 주문 생성을 하나씩만 돌린다. 사용자 단위라 다른 사용자끼리는 기다리지 않고, 3초 안에 못 잡으면 409(`TIMEOUT_EXCEPTION`). ② **DB 재고 행 잠금** `InventoryRepository.findInventoryByProduct_Id`(`PESSIMISTIC_WRITE`): 같은 상품의 재고 행을 하나씩만 바꾼다. **같은 상품에 주문이 몰리면** 여기서 기다린다. 잠금 대기 시간 제한을 따로 두지 않아 409가 아니라 응답 지연과 DB 커넥션 점유로 나타날 것으로 본다(가설). 스트레스를 두 가지로 한다: ① 상품이 고르게 섞임 ② 모든 주문에 같은 인기 상품 1개 포함. ②에서 주문 생성 p95, Hikari 대기, Performance Insights의 행 잠금 대기, 실패 코드, 재고 정합성(음수 0)을 본다. 409가 나면 분산락(같은 사용자)인지 다른 원인인지 오류 코드와 로그로 나눈다 |

| 인증 | 다른 테스트에 포함 | 이메일 로그인, 소셜 로그인 | 2.5 RPS (통합 ×1의 로그인) | 스트레스 | BCrypt가 CPU를 써서 로그인이 몰리면 다른 API도 느려진다 (예전 기준 로컬 채팅 ×3에서 로그인 p95 9.3초). 로그인 RPS와 앱 CPU의 관계를 표로 남긴다 |
| 환불 | 새 기준 3종·한계 완료 (로컬, 분당 50세션 = 이 표 목표의 10배): 환불 p95 855ms, 안정 한계 ×250(초당 208건), Tomcat 스레드가 먼저 참 | 환불 요청 | 분당 5회 (1만 × 환불 2% ÷ 3,600초 × 1.5 ≈ 0.083 RPS, D의 1/5) | 부하, 스트레스 | 포트원 취소 지연은 테스트 채널에서 쟀다 (avg 807ms, p95 1.07s, README). 6-2의 `fake-cancel-delay`로 넣는다 |

- 결제·주문·환불은 새 기준으로 스크립트를 바꾸고 로컬에서 다시 쟀다 (각 README). 통합에서 여유가 있는지 보려고 이 표의 목표보다 높게(결제·주문 ×2, 환불 ×10) 잡았고 모두 통과했다. 목표와 통합 비율(3-2)은 이 표 값 그대로 쓴다
- 모든 도메인 테스트는 fake LLM으로 한다. 견적은 채팅 첫 메시지로 발급되지만 견적 테스트는 fake LLM으로 띄워 견적 처리만 잰다. 나머지 도메인은 LLM을 쓰지 않는다
- 같은 AWS 환경에서 두 도메인을 동시에 돌리지 않는다. 결과가 섞인다

### 8-3. 1단계 완료 기준
- 도메인마다 "×몇에서 무엇이 막혔는지"를 한 줄로 적을 수 있다
- 채팅은 "fake(실측 지연)에서 의도별 메시지 p95, 서버 처리 시간, Tomcat 점유"를 로컬 fake 결과와 비교한 표가 있다
- 로컬과 AWS 수치가 다르면 이유(CPU 분리, 네트워크, LLM 지연 설정)를 적는다

## 9. 2단계: 통합 부하

LLM은 **fake**다. 지연과 문장별 의도는 5-1·5-2 값을 쓴다 (채팅 도메인 테스트와 같은 설정).

### 9-1. 스크립트 구조
`load-test/integrated/` 아래에 둔다. 흐름마다 함수 하나, 시나리오 하나다.

```js
// load-test/integrated/integrated-load.js (구조 예시)
import { browse } from './journeys/browse.js';
import { quoteChat } from './journeys/quote-chat.js';
import { purchase } from './journeys/purchase.js';
import { myOrders } from './journeys/my-orders.js';

const VISITS_PER_MINUTE = 250 * Number(__ENV.MULTIPLIER || 1);
const SHARE = { browse: 0.4, quoteChat: 0.3, purchase: 0.2, myOrders: 0.1 };

// arrival-rate의 target은 정수만 받는다 (예: 250 × 0.1 × 0.5 = 12.5는 오류)
function rate(name, ratio) {
    return Math.round(VISITS_PER_MINUTE * SHARE[name] * ratio);
}

// 데우기 5분은 판정에서 뺀다. 데우기와 측정을 시나리오로 나누고 phase 태그를 붙여, 기준은 phase:steady에만 건다
const WARMUP = '5m';
const STEADY = '20m';
// 측정이 끝난 뒤 진행 중인 방문을 기다리는 시간. B(약 75초)가 가장 길어 그보다 길게 잡는다
const GRACEFUL_STOP = '120s';

// VU는 3-3의 예상 VU(A 28, B 94, C 46, D 2.5)에 여유를 둔다
const VUS = { browse: [40, 100], quoteChat: [140, 400], purchase: [70, 200], myOrders: [5, 20] };

function warmup(name) {
    return {
        executor: 'ramping-arrival-rate',
        startRate: 0,
        timeUnit: '1m',
        // 3분 동안 절반까지 올리고, 2분 동안 목표까지 올린다
        stages: [
            { duration: '3m', target: rate(name, 0.5) },
            { duration: '2m', target: rate(name, 1) },
        ],
        preAllocatedVUs: VUS[name][0],
        maxVUs: VUS[name][1],
        // 데우기가 끝날 때 진행 중인 방문은 끊지 않고 마저 끝낸다 (끝난 요청은 phase:warmup으로 남는다)
        gracefulStop: GRACEFUL_STOP,
        exec: name,
        tags: { journey: name, phase: 'warmup' },
    };
}

function steady(name) {
    return {
        executor: 'constant-arrival-rate',
        rate: rate(name, 1),
        timeUnit: '1m',
        startTime: WARMUP,
        duration: STEADY,
        preAllocatedVUs: VUS[name][0],
        maxVUs: VUS[name][1],
        gracefulStop: GRACEFUL_STOP,
        exec: name,
        tags: { journey: name, phase: 'steady' },
    };
}

export const options = {
    scenarios: Object.fromEntries(Object.keys(SHARE).flatMap((name) => [
        [`${name}Warmup`, warmup(name)],
        [`${name}Steady`, steady(name)],
    ])),
    thresholds: {
        'http_req_failed{phase:steady}': ['rate<0.01'],
        'http_req_failed{phase:steady,kind:payment}': ['rate<0.001'],
        'http_req_duration{phase:steady,name:autocomplete}': ['p(95)<200'],
        'http_req_duration{phase:steady,api:read}': ['p(95)<500'],
        'http_req_duration{phase:steady,name:login,loginType:email}': ['p(95)<500'],
        'http_req_duration{phase:steady,name:login,loginType:social}': ['p(95)<2000'],
        'http_req_duration{phase:steady,api:write}': ['p(95)<1000'],
        'http_req_duration{phase:steady,kind:payment}': ['p(95)<1500'],
        'http_req_duration{phase:steady,api:ai}': ['p(95)<20000'],
        'dropped_iterations{phase:steady}': ['count==0'],
    },
};

export { browse, quoteChat, purchase, myOrders };
```

- 요청마다 `name`(API), `api`(read, write, ai. k6가 `group` 태그를 이미 쓰므로 다른 이름), 결제 요청은 `kind:payment`, 채팅 메시지는 `intent`(기대 의도) 태그를 붙인다. 섞어서 보내도 API별, 의도별로 나눠 볼 수 있다
- 기준(threshold)은 **데우는 5분을 빼고** 판정한다. 위처럼 데우기·측정 시나리오에 `phase` 태그를 붙이고 기준을 `phase:steady`에만 건다. k6가 출력하는 이 값이 공식 판정이다
  - 데우기 시나리오가 끝날 때 진행 중이던 방문은 `gracefulStop` 동안 마저 끝나므로, 측정 구간 처음 약 2분에는 `phase:warmup` 요청이 섞여 서버 부하가 목표보다 조금 높다. 서버 지표는 측정 시작 2분 뒤부터 본다
  - CSV에서 보낸 시각(7장)으로 다시 계산한 값은 확인용으로만 쓴다
- **방문(세션)을 상태별로 센다.** 진행 중이던 방문이 끝에 잘리면 그만큼 요청이 빠지기 때문이다 (로컬 채팅 스트레스에서도 끝날 때 마치지 못한 세션이 있었다)

  | 상태 | 세는 방법 |
  |---|---|
  | 시작한 방문 | 흐름 함수 첫 줄에서 `Counter` `visit{state:started}` +1 |
  | 정상 완료 | 흐름 마지막 요청까지 성공하면 `visit{state:completed}` +1 |
  | 오류로 중단 | 중간 요청이 실패해 `return`할 때 `visit{state:aborted, step:...}` +1 |
  | 시작하지 못함 | k6 `dropped_iterations` (VU가 모자라 보내지 못한 방문) |
  | 테스트 종료로 중단 | k6 출력의 `interrupted` 반복 수. 확인용으로 started − completed − aborted와 맞춰 본다 |

  - 종료 유예시간은 `gracefulStop: 120s`다. 측정 20분이 끝나면 새 방문은 시작하지 않고, 진행 중인 방문만 120초까지 기다린다
  - 새 방문이 멈춘 뒤 서버에 남은 작업이 0으로 내려가는지 본다: `zelo_chat_inflight`, `tomcat_threads_busy_threads`, `hikaricp_connections_active`. 0이 되기까지 걸린 시간도 결과서에 적는다
- 로그인은 방문마다 한다. 토큰을 setup에서 미리 받아 두면 access 토큰이 10분 뒤 만료되고(`jwt.access-expiration`), 실제처럼 로그인 비용도 들어가지 않는다
- 채팅 응답은 의도에 따라 payload가 다르다. fake에서는 견적 요청이 `QUOTE_CARD`, 견적 수정·리뷰·일반 질문은 텍스트 답변이다(fake 견적 수정은 카드 대신 질문을 돌려준다, 5-0). 통합에서는 이 형식만 check하고, 응답 내용과 실제 의도는 채팅 도메인 부하에서 본다 (3-2)

### 9-2. 흐름별 상세

**A. 둘러보기** (사용자 없음)
1. `GET /api/categories`
2. `GET /api/products/popular`
3. `GET /api/products/popular-keywords`
4. `GET /api/products/autocomplete` × 2 (검색어 앞 1글자, 2글자)
5. `GET /api/products?keyword=...` (검색어 목록에서 무작위. 흔한 것 70%, 드문 것 25%, 결과 없는 것 5%)
6. 같은 검색의 2쪽
7. `GET /api/products/{productCode}` × 2 (검색 결과에서 고름)

**B. 견적·질문** (5,001\~15,000)
1. 로그인 (3-5 규칙: 이메일 70%, 소셜 fake 30%)
2. `GET /api/chat/rooms`
3. `POST /api/chat/messages` (견적 요청) → `roomId`
4. `POST /api/chat/rooms/{roomId}/messages` × 4 (인분 변경, 견적 수정, 리뷰 질문, 일반 질문)
5. `GET /api/chat/rooms/{roomId}/messages`

**C. 구매** (20,001\~25,000)
1. 로그인 (3-5 규칙: 이메일 70%, 소셜 fake 30%)
2. `GET /api/chat/rooms`
3. `POST /api/chat/messages` (견적 요청) → `roomId`
4. `POST /api/chat/rooms/{roomId}/messages` × 2 (인분 변경, 견적 수정). 마지막으로 받은 견적 카드의 `quoteId`를 쓴다 (fake에서는 견적 수정이 카드를 주지 않아 인분 변경 카드가 마지막 카드다)
5. `GET /api/users/me/addresses`
6. `GET /api/payment-methods`
7. `POST /api/orders/confirmations` (`roomId`, `quoteId`)
8. `POST /api/orders` (`quoteId`, 7번의 `confirmationId`. 배송지는 구매 확인이 고른 기본 배송지) → `orderId`, `portoneId`
9. `POST /api/payments/{portoneId}/payment-method` (등록 카드)
10. `GET /api/orders/{orderId}`

- 견적 카드를 하나도 받지 못하면 7번부터 하지 않고 끝낸다. 이 경우는 HTTP 실패가 아니라 응답 형식 check 실패로 센다
- **구매 단계별 도달 건수를 따로 센다.** k6 `Counter` `purchase_step`에 `step` 태그를 붙여 단계마다 1씩 더한다

  | 단계 (`step`) | 세는 시점 |
  |---|---|
  | `started` | 로그인 성공 |
  | `quote_ready` | 3번에서 견적 카드를 받음 |
  | `order_tried` / `order_ok` | 8번 요청 전 / 8번 201 |
  | `payment_tried` / `payment_ok` | 9번 요청 전 / 9번 결제 성공 |
  | `completed` | 10번 주문 상세에서 결제 완료 상태 확인 |

  - 예: 구매 1,000건이 시작됐는데 결제 요청이 600건이면 "결제 600건을 잘 처리했다"와 "목표 구매 부하를 처리했다"는 다른 결론이다. 결과서에는 단계별 건수와 단계 사이 비율을 같이 적는다
  - 통합 C는 그대로 두고, 주문·결제가 목표 요청량을 실제로 받는지는 1단계 주문·결제 **단독** 테스트(8-2)로 확인한다. 단독 테스트는 시드 견적·시드 주문으로 시작해 앞 단계 실패에 영향받지 않는다
- 견적은 Redis에서 10분 뒤 만료되므로 3\~8번이 10분 안에 끝나야 한다. 생각 시간을 넣어도 1분 안쪽이라 문제없다
- 요청 본문은 `http/zelo-scenario.http`와 각 Request DTO에 맞춘다

**D. 내 주문 확인** (25,001\~27,000)
1. 로그인 (3-5 규칙: 이메일 70%, 소셜 fake 30%)
2. `GET /api/orders`
3. `GET /api/orders/{orderId}` (목록 첫 건)
4. 5번 중 1번 `POST /api/orders/{orderId}/refund`. 같은 주문을 두 번 환불하지 않도록 사용자 번호를 돌려 쓴다 (25분 테스트에서 D 방문은 약 560회라 2,000명이 한 번씩도 다 돌지 않는다)

### 9-3. 유지 시간을 20분으로 한 이유
- 로컬 채팅 부하에서 230\~260초 구간에 Hikari가 꽉 찬 일이 있었다. 몇 분짜리 테스트에서는 이런 일시적인 현상이 우연인지 반복되는지 구분할 수 없다
- 처음에는 실제 OpenAI 호출 비용 때문에 30분에서 20분으로 줄였다. 지금은 모두 fake라 비용이 들지 않는다. 길이는 20분으로 두고, 더 길게 봐야 하면 늘린다 (AWS 사용 시간만 는다)
- **토큰·견적 만료 경로는 이 테스트로 검증하지 않는다.** 방문마다 새로 로그인하고 새 견적을 1분 안팎에 쓰므로, 테스트가 20분이어도 만료된 access 토큰(10분)이나 만료된 견적(10분)을 쓰는 행동은 생기지 않는다. 이번 범위에 넣지 않았고, 필요하면 만료된 값을 일부러 쓰는 흐름을 따로 만든다

### 9-4. 통합에서만 볼 수 있는 것 (결과서에 꼭 넣는다)
1. 채팅 메시지가 몰리는 순간에 상품 조회 p95가 같이 오르는지 (시간대별로 겹쳐 그린다)
2. 앱 1대와 2대의 차이: 처리량이 2배 가까이 늘어나는지, 아니면 RDS, Redis에서 막히는지. 실제 OpenAI 한도(5-0)는 fake라 볼 수 없으므로 분당 토큰을 계산해 같이 적는다

## 10. 3단계: 통합 스트레스

| 항목 | 값 | 이유 |
|---|---|---|
| LLM | **fake** (실측 지연 5-1, 문장별 의도 5-2. 통합 부하와 같은 설정) | 실제 OpenAI는 한도(5-0)에 먼저 막힌다 |
| 배수 | ×1, 1.5, 2, 2.5, 3 | 로컬 새 기준 채팅 한계가 메시지 약 20 RPS(Tomcat 200, fake 메시지 약 9.7초)였다. 통합 ×k에서 메시지는 8.75k RPS라, 스레드가 먼저 차고 메시지 시간이 fake와 같다고 가정하면 ×2.3 근처에서 Tomcat이 찬다(가설). 실제 메시지가 더 짧으면 더 위에서 막히고, 다른 자원이 먼저 차면 더 아래에서 막힌다. ×3이면 그 너머도 볼 수 있다. fake라 OpenAI 비용이 없으므로 ×3에서도 막히지 않으면 ×4를 더한다 |
| ×1 단계 | 통합 부하와 비교 | 통합 부하와 트래픽·LLM 설정이 같다. 두 결과의 차이로 같은 조건 두 번의 흔들림 폭을 본다 (11-2) |
| 단계 길이 | 올리기 30초 + 유지 3분 | 메시지 하나가 20초 안쪽이라 3분이면 단계마다 메시지가 충분히 쌓인다. 분석에서는 각 단계의 처음 30초를 뺀다. 스크립트가 요청마다 보낸 시각으로 `stage` 태그(올리기 `ramp`, 유지 `x1`·`x1_5`·…, 마지막 단계 뒤 `end`)를 붙여 요약에 단계별 값이 바로 나온다 |
| 총 길이 | 약 18분 | |
| 멈춤 조건 | 한 단계의 유지 구간 요청만 모아 실패율 10% 초과 또는 p95가 기준의 5배를 넘으면 바로 멈춘다. 채팅(`api:ai`)은 실패율로만 멈춘다 | 그 뒤는 볼 것이 적다. k6 `abortOnFail`을 단계별 태그(`{stage:xN}`)에 건다. 테스트 전체 누적으로 보면 앞 단계의 정상 요청에 묻혀 늦게 멈춘다. k6에는 "기준을 넘는 상태가 N분 계속"을 거는 기능이 없다(`delayAbortEval`은 테스트 시작부터 판정을 미루는 시간이다). 채팅 기준 20초의 5배(100초)는 요청 timeout 40초보다 길어 p95로는 걸리지 않고, 30초 시간 예산 초과(504)와 timeout이 실패율에 잡힌다 |
| 원인 확인 실험 | 7-2 | 스트레스에서 의심되는 원인이 나오면 같은 fake 환경에서 그 조건 하나만 바꿔 확인한다 (예: 상품 조회량 고정, 채팅량만 증가) |

### 기록할 것 (단계별, 보낸 시각 기준)
- API 묶음별 p95, 실패율, 실제 처리량(초당 성공 메시지, 주문)
- 의도별 메시지 p95, 서버 처리 시간 (메시지 시간 − LLM 시간)
- fake LLM 시간(operation별 p95. 설정한 분포대로 나왔는지 확인용), 서킷 상태
- Tomcat, Hikari, 앱 CPU, RDS CPU 중 **가장 먼저 한계에 닿은 것**. 실제 OpenAI 한도는 fake라 볼 수 없으므로, 그 배수의 분당 토큰을 계산해 5-0 한도(분당 200만)와 비교한 값을 따로 적는다
- 원인 문장은 7-2 표의 몇 단계까지 확인했는지 함께 적는다
- 실패 코드 분포 (`zelo_api_error_total{code}`, `zelo_chat_fallback_total{code}`)
- 결과 한 줄 예: "×2.5에서 Tomcat 스레드 200개가 채팅 요청으로 차며 상품 조회 p95가 0.05초에서 2.1초로 올랐다. 원인은 LLM을 기다리는 동안 스레드를 잡는 채팅 요청"

## 11. 4단계: 고치고 다시 재기

### 11-1. 고칠 후보 (지금까지 찾은 것)

| 후보 | 담당 | 근거 | 기대 효과 |
|---|---|---|---|
| 견적 발급이 DB 커넥션을 오래 잡는 구간 줄이기 **(#411에서 고침)** | 견적 담당 | 로컬에서 커넥션 1개를 1.1\~2.5초 사용, ×3에서 대기 평균 5.04초. 수정 뒤 로컬 채팅 부하의 커넥션 대여 1회 평균 40ms(모든 대여의 평균), 로컬 채팅 한계 메시지 3.8 → 20 RPS | AWS에서는 전·후 비교 대상이 아니다. 고친 코드로 잰다 |
| `connection-timeout` 30초 → 더 짧게 | 팀 | 30초 동안 기다린 뒤 500이 난다. 그동안 Tomcat 스레드도 잡혀 있다 | 막힐 때 빨리 실패해 스레드를 돌려준다 |
| Hikari 풀 크기 | 팀 | AWS 시작 값 30 (6-2). HikariCP 문서는 `(DB CPU 코어 수 × 2) + 디스크 수`에서 시작하라고 한다 | AWS 사양에 맞는 값. 앱 2대면 RDS 커넥션 수 한도도 함께 본다 |
| 채팅 동시 처리 제한 (Bulkhead) | 채팅 | 새 기준 로컬 채팅 스트레스 ×2.5에서 Tomcat 200개가 채팅 요청으로 찼다. LLM 응답이 길면 더 빨리 찬다 | 채팅이 몰려도 다른 API 스레드가 남는다 |
| LLM을 기다리는 동안 스레드를 잡지 않게 하기 (가상 스레드 `spring.threads.virtual.enabled`, 비동기 응답) | 채팅 | 위와 같다. 로컬에서는 LLM을 기다리는 채팅 요청이 스레드를 잡아 Tomcat 200이 찼다 | 요청 스레드 포화가 병목이라면 한계가 다른 자원으로 옮겨 간다. 후보는 DB 커넥션, CPU, OpenAI 한도다. DB 커넥션 쪽 한계(풀 10개일 때 약 55 RPS, 30개면 약 160 RPS)는 검증한 최대치가 아니다. 로컬 저부하에서 잰 메시지당 커넥션 사용(4.6회 × 40ms)이 고부하에서도 그대로라고 가정한 추정이다. Java 21에서 `synchronized` 안에서 기다리는 코드는 스레드를 놓지 못하므로 확인한다 |

### 11-2. 다시 잴 때 지킬 것

1. **한 번에 하나만 바꾼다.** 코드 수정과 풀 크기 변경을 같이 하면 어느 쪽 효과인지 알 수 없다
2. **조건을 같게 한다**
   - 같은 인스턴스 타입, 같은 시드, 같은 k6 스크립트와 버전, 같은 앱 설정, 같은 fake 설정
   - 결과서에 커밋 해시와 바꾼 것 하나를 적는다
   - 프롬프트(`src/main/resources/prompts`)를 바꾸는 수정은 fake로 효과를 볼 수 없어 이번 범위에서 다루지 않는다
3. **데우는 방식도 같게 한다.** 첫 실행은 DB 버퍼 캐시가 비어 있어 느리다. 전·후 모두 앱 재시작 → 데우기 5분 → 측정으로 맞춘다
4. **LLM 조건을 전·후 같게 한다.** 통합 부하·스트레스 모두 전·후 **같은 fake 설정**(5-1·5-2 값 그대로)으로 한다. 고친 뒤에 fake 값을 바꾸면 LLM 조건과 고친 것의 효과가 섞인다
5. **LLM 조건이 전·후 같다.** 모두 fake라 전·후 차이는 우리 서버 변화다. fake LLM 시간(operation별 p50·p95)을 표에 같이 적어 설정대로 나왔는지 확인한다. 한계(SLO를 지킨 최대 배수)는 통합 스트레스 전·후로 판단한다
6. **같은 지표로 비교한다.** 전·후 표에는 같은 API의 p95, 같은 단계의 처리량, 같은 히스토그램을 쓴다. `_max`는 쓰지 않는다
7. **흔들림 폭을 알고 비교한다.** 같은 조건 두 번의 차이를 전·후 각각 잰다. 통합 부하와 스트레스 ×1은 같은 조건이라 이 둘을 쓰고, 필요하면 한 번 더 돌린다. 전·후 차이가 같은 조건 두 번의 차이보다 작으면 "차이 없음"으로 적는다
8. **병목이 옮겨 갔는지 본다.** DB 대기가 사라져도 CPU, Tomcat에서 다시 막힐 수 있다. 처리량 한계가 얼마나 올랐는지와 새 병목을 같이 적는다
9. **정합성을 다시 확인한다.** 빨라지게 고치다가 락 범위를 줄이면 재고가 음수가 되거나 중복 주문이 생길 수 있다. 4-1-3의 정합성 쿼리를 매번 돌린다
10. **로컬과 AWS 수치를 섞어서 비교하지 않는다.** 전·후 비교는 같은 환경 안에서만 한다
11. 개선 전 결과 파일은 지우지 않고 `before/`, `after/`로 나눠 남긴다

| 서킷이 열리면 결과가 바뀜 | fake에는 429가 없어 서킷이 열리면 시간 초과나 서버 쪽 원인이다. 실제 OpenAI에서는 429로 열렸다 (5-0) | 서킷 상태를 단계별로 기록하고, 열린 구간은 따로 표시한다 |
| 다른 외부 서비스는 fake | 포트원, 소셜 로그인의 실제 변동이 없다. 포트원 웹훅은 아예 돌지 않는다 | 지연 값은 실측으로 맞추고, 결과서에 "포트원 fake, 웹훅 미포함"이라고 적는다 |
| 시드 데이터 분포 | 시드 주문과 방은 실제보다 고르게 퍼져 있다 | 인기 상품 몰림은 8-2 주문 ②로 따로 잰다 |
| 로컬 결과와 다름 | CPU, 디스크, 네트워크, LLM이 다르다 | 로컬 결과는 "같은 경향인지"만 보고 숫자는 AWS 결과를 쓴다 |
