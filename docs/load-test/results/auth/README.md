# 인증(로그인) 부하 테스트 결과 정리

대상: `POST /api/users/login` (이메일 로그인, BCrypt 검증). 팀 목표 RPS는 0.44.
환경: Apple M4 8코어(성능 4 + 효율 4), 8GB. 앱, DB, Redis, k6가 한 대에서 동작. k6는 도커로 실행.

## 외부 api 속도

| 대상 | 1차 | 2차 | 평균 |
| -- | -- | -- | -- |
| Google (Token, UserInfo) | 0.56 + 0.44 | 0.46 + 0.33 | 약 0.9 |
| Kakao (Token, UserInfo) | 0.89 + 0.18 | 0.49 + 0.16 | 약 0.86 |
| 메일 전송(SES) | 0.75 | 0.52 | 약 0.6 |

첫 호출을 제외한 1,2회 호출 평균값

## 요약: 단계별 결과

| 실행 | 마지막 통과 | 처음 실패 | 실패 때 서버 상태 |
| -- | -- | -- | -- |
| 02 풀 10 | 60 RPS | 80 RPS (p95 508ms) | 앱 CPU 87~89%, Hikari 10/10에 대기 22~25 |
| 03 풀 30 | 60 RPS | 80 RPS (p95 669ms) | 앱 CPU 70%, Hikari 사용 16, 대기 4 |
| 04 풀 30 + 전체 CPU | 40 RPS | 60 RPS (p95 508ms) | 앱 CPU 80%, **전체 CPU 100%**, Hikari 30/30, 대기 2 |
| 05 04 재측정 | 40 RPS | 60 RPS (p95 538ms) | 앱 CPU 82%, **전체 CPU 100%**, Hikari 사용 23, 대기 16 |

## 1. 풀 10일 때 (02)

- 20 RPS까지는 p95가 84~122ms로 스모크 기준선(83ms)과 같았다.
- 40 RPS부터 풀 10개가 모두 사용 중이 되고 대기 커넥션이 생겼다(8개). 60 RPS에서는 대기 22개, p95 458ms.
- 80 RPS에서 p95가 508ms를 넘어 중단됐다. Tomcat busy 35 = Hikari 사용 10 + 대기 25로, 요청이 DB 커넥션 풀 앞에 줄 서 있었다.
- 이때는 앱 CPU(87~89%)와 풀 포화가 함께 나타나서 둘 중 무엇이 원인인지 분리할 수 없었다.
  로그인이 읽기 트랜잭션이라 BCrypt 검증(약 80ms) 동안 커넥션을 쥐기 때문에, 풀이 BCrypt 동시 실행 수를 약 10으로 제한하는 효과가 있었다.

## 2. 풀을 30으로 늘렸을 때 (03)

- 60 RPS의 p95가 458ms에서 **102ms**로, Hikari 대기가 22에서 **0**으로 줄었다. 60 RPS까지는 풀이 병목이었다.
- 그래도 80 RPS에서 p95 669ms로 실패했다. 앱 CPU는 70%였다.
- 풀을 늘렸는데도 한계가 같은 구간(60~80)에 남았으므로 풀만의 문제가 아니었다.
  다만 이때는 앱 프로세스 CPU만 측정해서 "CPU가 포화였는지" 판단하기 부족했다.

## 3. 컴퓨터 전체 CPU 지표를 추가해서 봤을 때 (04)

- 60 RPS에서 **컴퓨터 전체 CPU가 100%**였다(앱 CPU는 80%). 앱 외에 DB, Redis, k6, 도커가 같은 머신에서 CPU를 나눠 쓰고 있었다.
- 이때 Hikari 사용이 풀 크기(30)에 도달하고 대기가 2개 생겼다. CPU가 부족해 BCrypt가 느려지면 커넥션을 쥐는 시간이 길어져 풀도 같이 찬 것으로 보인다. 풀이 원인이라기보다 CPU 포화의 결과다.
- 결론: 풀 크기가 먼저 막는 구간(02)을 지나면, 한계는 **머신 CPU 포화**로 결정된다. 병목은 BCrypt의 CPU 사용이라는 가설과 맞다.

## 주의: 실행마다 한계가 달랐다

- 03과 04는 같은 설정(풀 30)인데 한계가 60~80(03)과 40~60(04)으로 한 단계 다르다.
- 04의 20 RPS 단계 p95가 177ms로 튀고 전체 CPU가 83%였던 점으로 보아, 실행 시점에 머신의 다른 작업이 영향을 줬을 수 있다.
- 05(재측정)도 04와 같이 40 통과, 60 실패였다. 리뷰 반영 후 다시 측정한 11은 60 통과, 80 실패였다(단계별 평가 지연으로 바꿔도 편차가 사라지지 않아, 편차는 CPU가 100%에 붙은 머신 상태 때문으로 본다). 풀 30의 4번 중 2번이 40~60, 2번이 60~80(03, 11)이라 한계는 "**약 40~80 RPS**"(대체로 60 RPS 근처)로 말하는 것이 정직하다. 목표(0.44 RPS)의 약 90~180배 이상이라는 결론은 어느 실행에서도 같다.
- 한계를 좁히려면 같은 설정으로 반복 측정하고, 다른 프로그램을 끈 상태에서 돌린다.

## 이메일 로그인과 소셜 로그인은 무엇이 다른가

같은 "로그인"이지만 요청이 서버에서 시간을 쓰는 곳이 달라서 한계의 모양이 다르다.

| | 이메일 로그인 (02~05) | 소셜 로그인 (06~07) |
| -- | -- | -- |
| 팀 목표 RPS | 0.44 (2,000명 × 70% × 1.5회 ÷ 7,200초 × 1.5) | 0.19 (2,000명 × 30% × 1.5회 ÷ 7,200초 × 1.5) |
| 요청이 시간을 쓰는 곳 | BCrypt 검증(서버 CPU, 약 80ms) | 소셜 서버 응답 대기(fake 평균 900ms ±50%, 서버 스레드가 놀면서 기다림) |
| 스모크 p95 | 83ms | 1,355ms (대부분 fake가 만든 값) |
| 스트레스 한계 | **약 40~80 RPS** (대체로 60 근처) | **약 200~240 RPS** |
| 목표 대비 | 약 90~180배 | 약 1,000배 이상 |
| 막힌 곳 | **머신 CPU** (BCrypt). 앱 CPU 80~90%, 전체 CPU 100% | **Tomcat 스레드 200개**. 앱 CPU 최대 21%, 전체 CPU 최대 47% |
| 동시에 묶이는 스레드 | 적음 (요청이 80ms로 짧음) | 많음 (동시 요청 수 = RPS × 0.9초, 200 RPS에서 약 190개) |
| DB 커넥션 풀(Hikari) | 풀 10이면 먼저 막힘(BCrypt 동안 커넥션을 쥠). 풀 30이면 한계가 CPU로 이동 | 사용 1~3개뿐. 외부 호출 중에는 커넥션을 쥐지 않음 |
| 한계를 정하는 값 | CPU 코어 수와 BCrypt 비용 | 스레드 수 ÷ 외부 응답 시간 (200 ÷ 0.9초 ≈ 222 RPS) |
| 외부 요인에 대한 민감도 | 낮음 (외부 호출 없음) | **높음**. 실제 소셜 서버가 2초로 느려지면 한계가 약 100 RPS로 내려감 |
| p95 한도 | 500ms | 2,000ms (정상 응답 최대가 약 1.4초라서 로그인과 같은 기준을 쓸 수 없음) |
| 개선 방향 | BCrypt 비용, 서버 CPU 증설 | 스레드 수 증설, 소셜 호출 타임아웃, 비동기(논블로킹) 호출 |

- 소셜 로그인의 스트레스 한계는 서버 실력이 아니라 **fake 지연 평균에 달린 값**이다. 지연 설정을 바꾸면 다시 측정해야 한다.
- 같은 서버에서도 둘 중 먼저 한계가 오는 것은 이메일 로그인이다. 팀 목표 기준으로 둘 다 여유가 크다.

## 소셜 로그인 스트레스 결과 (07)

- 200 RPS까지 통과(p95 약 1.31초)하고 240 RPS에서 p95 2,006ms로 기준을 넘어 중단됐다.
- 200 RPS까지 p95가 1.29~1.34초로 같다. fake 지연의 상한(1,350ms)과 같아서, 서버가 요청을 더 느리게 만들지 않았다는 뜻이다.
- Tomcat busy 스레드는 RPS × 0.9와 맞게 늘었다 (40 RPS에서 40, 80에서 78, 120에서 117, 160에서 151, 200에서 190). 240 RPS에서 200개에 닿았다.
- 한계: 1회 측정, 240 RPS 단계는 중단으로 6,398건만 보냈고 그 단계에서 k6의 VU가 최대(400)에 닿았다(408). 그래서 "200~240 사이"로 말한다.

## 토큰 재발급 결과 (08 스모크, 10 스트레스)

- 팀 목표 약 5 RPS (2,000명 × 접속 중 액세스 토큰 10분 만료마다 최대 12회 ÷ 7,200초 × 1.5. 2시간 내내 접속한다는 가정이라 팀 확정이 필요하다).
- 스모크(08): 평균 0.7ms, p95 0.9ms. 로그인(83ms), 소셜 로그인(약 880ms)보다 훨씬 가볍다.
- 스트레스(10): 5 → 2000 RPS 9단계 모두 통과, 도달률 99~100%. 한계는 **2000 RPS보다 높다**(목표의 400배 이상).
- 서버 자원은 여유가 있다. 앱 CPU 최대 27%, Tomcat busy 최대 33. 재발급은 DB를 쓰지 않는다(Hikari 사용 0~4, 복구 로그인과 스케줄러의 몫).
- 1600 RPS 단계에서 컴퓨터 전체 CPU가 85.5%였다. 앱 CPU는 27%뿐이라 k6와 DB, Redis의 몫이 컸다. 한 대로는 2000 RPS 이상의 한계를 측정하기 어렵다.

| DB 사용 | 사용 (읽기 트랜잭션) | 거의 안 씀 | 쓰지 않음 |

## 재발급 실패 조사

### 증상
- 스모크 2번, 스트레스 첫 실행에서 요청 일부가 실패했고, 실패한 VU는 이후 요청을 보내지 못했다(스크립트가 같은 토큰을 다시 쓰면 서버가 세션을 지우기 때문에 멈추게 설계했다).
- 스트레스 첫 실행(09)에서는 실패 24건 때문에 VU 24개가 멈췄고, 전체 반복의 59%가 요청 없이 끝나서 결과가 무효였다. 실패 시점에 서버 로그에는 실패 로그가 없고 "로그인 완료" 로그가 있었다.

### 확인된 사실
- 스크립트를 고친 뒤(10): 실패 78건(전체 376,991건의 0.02%)은 **모두 상태 0**(응답을 받지 못한 연결 오류)이다. 서버가 거절한 응답(401, 409, 429, 5xx)은 0건이다.
- 그래서 서버 로그에 실패가 남지 않았다. 서버가 거절한 것이 아니라 응답이 오지 않은 것이다.
- "로그인 완료" 로그는 수정한 스크립트의 복구 동작이다. 재발급이 실패하면 그 사용자를 다시 로그인시켜 새 토큰을 받는다(78회). 서버 쪽에서 세션이 꼬여서 생긴 로그인이 아니다.
  (09 이전 실행에는 복구 로그인이 없었다. 그 실행의 로그인 완료 로그는 준비 단계의 로그인이거나 다른 요청일 수 있어서, 같은 설명이 맞는지는 확인하지 못했다.)

### 아직 모르는 것 (가설 포함)
- 왜 응답을 받지 못했나. 짐작되는 후보는 있지만 확인하지 못했다: 서버가 닫는 중인 연결을 k6가 재사용(Tomcat은 연결 하나로 처리하는 요청 수와 유휴 시간에 제한이 있다), 도커를 거치는 네트워크의 연결 오류, 같은 머신에서 k6가 연결을 많이 여는 데서 오는 자원 한계.
- 서버가 처음 요청을 처리했는지(토큰이 이미 바뀌었는지)도 모른다. 처리했다면 응답이 유실된 것이라 실제 서비스에서도 사용자가 재시도하면 "이미 교체된 토큰" 오류를 볼 수 있다.

### 다음에 확인할 것
- `reissue-stress.js`에 진단을 추가했다. 응답을 못 받은 실패마다 같은 토큰으로 한 번 더 보내서 결과를 센다.
  - 재시도가 성공하면: 서버가 처음 요청을 처리하지 않은 것(연결 문제)
  - 재시도가 "이미 교체된 토큰"으로 실패하면: 서버는 처리했는데 응답이 유실된 것
- 실패 로그에 k6의 오류 코드와 오류 문구도 남긴다(`연결 재설정`, `EOF`, `시간 초과` 구분).

## 한계(이 결과로 말할 수 없는 것)

- 한 대에서 앱, DB, Redis, k6를 같이 돌린 값이라 AWS에서는 달라진다. 특히 이 머신은 전체 CPU 100%까지 가서 로컬 한계가 일찍 온다.
- 지표는 2초마다 찍은 순간값이며, 각 지표의 최대는 서로 다른 순간일 수 있다.
- 03에는 전체 CPU 지표가 없다. 02, 03의 "CPU"는 앱 프로세스 CPU다.
- 03의 s05 앱 CPU 140.8%는 비정상 이상값이다(100% 초과 불가).
- 80 RPS 단계는 중단 때문에 몇 초분만 측정된다(03에서 205건).
