# 채팅 부하 테스트 결과 (스모크 · 부하)

- 실행일: 2026-11-04
- 브랜치: `feat/393-chat-seed`
- 확인하려는 것: **AI 응답을 기다리는 동안 DB 커넥션을 붙잡지 않는가**
- 결과: **두 테스트 모두 통과했다. AI를 기다리는 동안 DB 커넥션을 붙잡지 않았다.**

## 1. 실행 환경

| 항목 | 값 |
|---|---|
| 앱 | 로컬 1대, `performance` 프로필 |
| DB | Postgres 16 (docker), Hikari 커넥션 최대 10개 |
| LLM | fake, 호출마다 3.5~6초 지연(`delay=3500ms`, `delay-max=6s`) |
| LLM 판단 | 항상 장보기 요청(`plan-intent=SHOPPING_REQUEST`) → 메시지마다 LLM 2번(메뉴 계획 + 답변) + 실제 견적 발급 |
| 데이터 | 사용자 시드 5,001~15,000번, 채팅방 105,000개·메시지 1,050,000건, 상품 약 10만 개 |

앱 실행 명령:

```bash
JWT_SECRET=... OPENAI_API_KEY=fake ./gradlew bootRun --args='--spring.profiles.active=performance --zelo.llm.fake.plan-intent=SHOPPING_REQUEST --zelo.llm.fake.mode=DELAY --zelo.llm.fake.delay=3500ms --zelo.llm.fake.delay-max=6s --zelo.seed.enabled=true --zelo.seed.load-test.enabled=true --zelo.delivery.scheduler.enabled=false'
```

## 2. 시나리오

세션 1개(`load-test/chat/chat-session.js`)는 아래 순서로 진행된다.

1. 로그인 `POST /api/users/login`
2. 방 목록 `GET /api/chat/rooms`
3. 새 채팅 시작 `POST /api/chat/messages` → 견적 카드 확인
4. 같은 방에 메시지 4번 `POST /api/chat/rooms/{roomId}/messages` → 매번 견적 카드 확인
5. 메시지 목록 `GET /api/chat/rooms/{roomId}/messages`

세션마다 다른 사용자를 쓴다(5001번부터 순서대로).

| | 스모크 | 부하 |
|---|---|---|
| 스크립트 | `chat-smoke.js` | `chat-load.js` |
| 방식 | 가상 사용자 3명 반복 | 분당 25세션 시작(`constant-arrival-rate`) |
| 시간 | 2분 | 5분 |
| 통과 기준 | 실패 0%, 체크 100% | 실패 < 1%, 체크 > 99%, 채팅 응답 p95 < 13초 |

분당 25세션은 하루 사용자 1만 명 중 2,000명이 피크 2시간에 채팅한다고 보고(분당 약 16.7명) 1.5배 여유를 둔 값이다. 메시지로는 초당 2.1건이다.

## 4. 부하 테스트 결과: 통과

### 4-1. k6 결과

부하 수치:

| 항목 | 설정·예상 | 결과 |
|---|---|---|
| 세션 시작 속도 | 분당 25세션 | 분당 25세션 (5분 동안 126개) |
| VU (동시에 진행 중인 세션) | 약 20 (25 × 48초 ÷ 60) | **평균 19.3, 최대 25** (미리 만든 VU 30개, 상한 100개) |
| 세션 1개 걸린 시간 | 약 48초 | 평균 53.8초, p95 57.4초 |
| HTTP RPS (전체 요청) | 약 3.3 | **3.3** (안정 구간 1분당 198~206건) |
| 메시지 RPS (채팅 메시지만) | 2.1 | **2.1** (630건 ÷ 300초) |
| 총 HTTP 요청 | 약 1,000건 | 1,008건 (세션당 8건) |

## 5. AI를 기다리는 동안 DB 커넥션을 붙잡지 않는가

### 근거 1. 커넥션 한 번 사용 시간 (가장 직접적인 근거)

`hikaricp_connections_usage_seconds` 히스토그램을 테스트 직전(`results/chat/chat-load-hikari-before.txt`)과 직후(`results/chat/chat-load-hikari-after.txt`)에 기록하고, 그 차이를 계산했다.

| 커넥션 한 번 사용 시간 | 횟수 | 비율 |
|---|---|---|
| 전체 | 2,922 | 100% |
| 0.1초 이하 | 2,157 | 73.8% |
| 1.07초 이하 | 2,716 | 92.9% |
| 2.15초 이하 | 2,893 | 99.0% |
| 3.58초 초과 | 15 | 0.5% |
| 5.73초 초과 | **0** | 0% |
| 가장 긴 사용 | 5.56초 | |

- 메시지 1건은 LLM을 2번 부르고, 두 번을 합치면 최소 7초다.
- 커넥션을 LLM 대기 내내 붙잡았다면, 메시지 630건마다 7초 넘는 사용이 1번씩 생겨야 한다. 실제로는 5.73초를 넘은 경우가 **0건**이었다.
- LLM 한 번(3.5~6초) 동안만 붙잡았다고 해도 630건이 모두 3.5초를 넘어야 한다. 실제로 3.58초를 넘은 경우는 15건뿐이었다.
- 이 15건은 견적 발급이 느렸던 경우다. 테스트 중 견적 발급 최대 시간(5.49초)과 커넥션 가장 긴 사용(5.56초)이 거의 같다.

### 근거 2. 처리 중인 채팅 수와 쓰고 있는 커넥션 수

채팅 요청은 평균 19.3건이 동시에 처리됐다. 같은 시점에 쓰고 있던 DB 커넥션은 평균 2.0개였고, 커넥션을 기다린 요청은 한 번도 없었다. 처리 중인 요청 대부분은 커넥션 없이 LLM 응답을 기다리고 있었다.

### 근거 3. 처리량

- 커넥션을 메시지 처리 내내(10.7초) 붙잡는다면, 커넥션 10개로 처리할 수 있는 메시지는 초당 10 ÷ 10.7 = 0.93건이다.
- 이번 테스트는 초당 2.1건을 보냈고, 실패 0건·커넥션 대기 0으로 처리했다.

## 6. 테스트 중 확인한 점

- **채팅 응답 p95(12.6~12.7초)가 기준 13초에 가깝다.** fake LLM 지연을 2번 합친 값(7~12초)과 견적 발급(평균 1.13초)이 더해진 결과다.
- **견적 발급이 혼자 보낼 때보다 느렸다.**
  - 메시지 1건만 보냈을 때 0.95초였고, 테스트 중 평균은 1.13초, 최대는 5.49초였다.
  - 이 시간 동안은 DB 커넥션을 쓴다.
  - 쓰고 있는 커넥션이 순간적으로 9개(최대 10개)까지 올라간 것도 이 구간이다.
  - 스트레스 테스트에서 트래픽을 올리면 이 구간이 커넥션 대기의 원인이 될 수 있다.
