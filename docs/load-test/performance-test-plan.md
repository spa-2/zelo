## 1. 목적과 범위

### 1-1. 목적
1. 예상 피크 트래픽에서 모든 도메인이 SLO를 지키는지 확인한다 (부하)
2. 트래픽을 올리면서 시스템 전체에서 **처음 막히는 자원**과 그때의 배수를 찾는다 (스트레스)
3. 한 도메인의 부하가 **다른 도메인에 주는 영향**을 수치로 확인한다
   - 로컬 채팅 스트레스에서 채팅만 늘렸는데 로그인 p95가 0.19초에서 9.3초로, 방 목록이 0.01초에서 3.4초로 늘었다 (`chat-load-test-result.md` 7장)
4. 실제 OpenAI의 응답 시간과 요청 한도 아래에서 채팅이 어떻게 동작하는지 확인한다 (채팅 도메인 부하, 통합 부하)
   - 로컬은 fake LLM(3.5\~6초 고정 범위)이라 실제 응답 시간의 흔들림, 의도 분류 결과, OpenAI 요청 한도가 빠져 있었다
   - 여기서 잰 실제 LLM 시간으로 스트레스용 fake LLM을 맞춘다 (5-0)
5. 찾은 병목을 고치고 **전·후 수치**를 남긴다

### 1-2. 범위

| 포함 | 제외 |
|---|---|
| 부하 테스트, 스트레스 테스트 (도메인별, 통합) | 스파이크, 장시간(soak), 장애 주입 테스트. 이번 범위가 아니다 |
| 사용자 API 전체 (인증, 상품, 채팅, 견적, 주문, 결제, 환불) | 관리자 API (`/api/admin/**`). 트래픽이 매우 적다. 관리자 리뷰 요약(`REVIEW_SUMMARY`)도 부르지 않는다 |
| **실제 OpenAI** (`LLM_MODE=real`): 사전 확인, 채팅 도메인 부하, 통합 부하 (고치기 전·후 1회씩) | 스트레스(고치기 전·후)의 실제 OpenAI. 비용 때문에 실측으로 맞춘 fake LLM으로 대신한다 (5-0) |
| | 실제 포트원, Google·Kakao, SES. 비용과 약관 문제라 fake로 대신하고 지연 값만 실측으로 맞춘다 |
| 스케줄러 (배송, 주문 만료, 결제 대조). 통합 테스트에서 켠다 | 프론트 화면 렌더링 시간 |

### 1-3. 실제 OpenAI로 바뀌면서 달라지는 것

| 항목 | 로컬 (fake) | AWS (실제) |
|---|---|---|
| 의도 분류 | `plan-intent=SHOPPING_REQUEST`로 모든 메시지가 견적 요청 | 메시지마다 실제로 분류된다. 견적 수정, 리뷰 조회, 일반 질문을 섞을 수 있다 |
| 메시지당 LLM 호출 | 2번 (메뉴 계획 + 견적 안내) | 의도마다 2\~3번 (5-1) |
| LLM 응답 시간 | 3.5\~6초 균등 | 실측 분포. 메뉴 계획 p95 약 7.5초 (`application.yaml` timeout 주석). 시간대에 따라 흔들린다. 2026-11-05 실제 메시지 10건: 메뉴 계획 1.5\~5.3초, 견적 안내 1.3\~1.8초, 견적 수정 계획 4.9\~7.8초, 메시지 하나 3.4\~6.9초(견적 수정 약 10초) |
| 외부 한도 | 없음 | OpenAI 계정의 분당 요청 수(RPM), 분당 토큰 수(TPM). 넘으면 429 |
| 비용 | 없음 | 호출 수 × 토큰 수만큼 든다. 실행할 때마다 승인을 받는다 (5-4) |

## 2. 진행 순서

| 단계 | 테스트 | 하는 일 | 찾는 것 | 실제 OpenAI |
|---|---|---|---|---|
| 0 | 사전 확인 (스모크) | 아주 적은 요청 | 스크립트, 시드, 환경이 맞는지. 호출당 토큰 수, 의도 분류 결과 | 약 290회 |
| 1 | 도메인별 부하·스트레스 | 도메인 하나씩 | 도메인 자체의 한계와 원인 | 채팅 부하만 약 15,100회 |
| 2 | **통합 부하 (1회)** | 모든 흐름을 비율대로 섞어 피크 목표로 | 피크에서 SLO를 지키는지, 도메인 간 영향. fake LLM을 맞출 실제 LLM 시간 | 약 26,100회 |
| 3 | **통합 스트레스** | 섞은 채로 ×1 → ×3, **fake LLM** | 시스템 전체의 첫 병목 | 없음 (fake) |
| 4 | **고치고 다시 재기** | 병목 하나를 고친 뒤 2단계(통합 부하, **실제**)와 3단계(통합 스트레스, **fake**)를 다시 한다 | 전·후 차이 | 통합 부하 약 26,100회 (스트레스는 fake) |

- 실제 OpenAI 합계 (고치기 1건 기준): 약 67,600회, 약 $19 (5-2)

### 순서를 이렇게 정한 이유
- **1단계를 2단계보다 먼저 하는 이유:** 섞은 테스트에서 느려지면 어느 도메인 때문인지 바로 알 수 없다. 도메인마다 한계와 원인을 먼저 알아 두면 통합 결과를 해석할 수 있다. 로컬 채팅 테스트에서도 단독 측정으로 견적 발급이 DB 커넥션을 1.1\~2.5초 잡는다는 원인을 찾았다
- **채팅은 1단계에서 부하만 실제 OpenAI로 하는 이유:** 채팅 단독 스트레스(×1\~×3)를 실제 OpenAI로 하면 호출이 약 47,100회(약 $13.5) 더 든다 (5-2). 채팅 단독 스트레스가 필요하면 fake LLM으로 한다. fake로 한 로컬 단독 스트레스 결과는 이미 있다 (`chat-dau50k-test-result.md`)
- **채팅 도메인 부하를 실제 OpenAI로 하는 이유:** 서버에 채팅만 있어서 느려진 원인을 OpenAI와 우리 서버로만 나누면 된다. 의도별 메시지 시간, 서버 처리 시간, AI 오류율을 다른 도메인 영향 없이 잰다. 로컬 fake 결과와 같은 목표·같은 스크립트라 바로 비교할 수 있다
- **통합 부하를 1회만 하는 이유:** 2회로 정했던 이유는 OpenAI 흔들림을 보고, 고치기 전·후 비교의 기준(같은 조건 두 번의 차이)을 만들려는 것이었다. 전·후 비교를 fake LLM으로 하기로 해서 두 번째 이유가 없어졌고, 흔들림은 측정 20분 동안의 시간대별 LLM 시간으로 본다. 다시 돌리는 조건은 9-3에 정했다
- **포트폴리오에서 중요한 단계:** 2 → 3 → 4. "피크 기준 통과 수치, 첫 병목, 고친 뒤 개선 폭"이 한 줄로 이어지기 때문이다

## 3. 목표 트래픽 (워크로드 모델)

### 3-1. 기본 가정

| 항목 | 값 | 근거 |
|---|---|---|
| DAU | 50,000명 | **가정.** 팀이 정한 새 기준. 상품·견적·채팅 테스트가 같은 값을 쓴다 (`load-test/product/README.md`, `load-test/quote/README.md`, `chat-session.js`) |
| 사용자당 하루 방문 | 1회 | **가정.** 장보기 앱이라 하루에 여러 번 오는 경우는 적다고 본다 |
| 피크 | 하루 트래픽의 20%가 1시간에 몰림 | **가정.** 저녁 장보기 시간대 |
| 피크 1시간 방문 | 50,000 × 20% = 10,000 | 새 기준의 "피크 1시간에 1만 명"과 같다 |
| 피크 분당 방문 | 10,000 ÷ 60분 = 166.7 | |
| 안전계수 | 1.5 | 기존 테스트와 같다. 가정이 틀렸을 때의 여유 |
| **피크 목표 (×1)** | **분당 방문 250회** | 166.7 × 1.5 |

- 예전 기준(DAU 1만, 하루의 20%가 2시간에 몰림 = 피크 2,000명)은 분당 방문 25회였다. 새 기준은 그 10배다

### 3-2. 방문 흐름(시나리오)과 비율

방문 한 번은 아래 네 흐름 중 하나다. 실제 사용자가 모두 결제까지 가지는 않으므로, 모든 사용자가 같은 사이클(로그인 → 견적 → 주문 → 결제)을 도는 방식으로 하지 않는다.

| 흐름 | 비율 | 분당 방문 (×1) | 요청 | 요청 수 |
|---|---|---|---|---|
| A. 둘러보기 | 40% | 100 | 카테고리 → 인기 상품 → 인기 검색어 → 자동완성 2번 → 검색 → 검색 2쪽 → 상세 2번 (로그인 없음, 상품 API는 인증 없이 열려 있음) | 9 |
| B. 견적·질문 | 30% | 75 | 로그인 → 방 목록 → 메시지 5개 (견적 요청, 인분 변경, 견적 수정, 리뷰 질문, 일반 질문) → 메시지 목록 | 8 |
| C. 구매 | 20% | 50 | 로그인 → 방 목록 → 메시지 3개 (견적 요청, 인분 변경, 견적 수정) → 배송지 조회 → 결제수단 조회 → 구매 확인 → 주문 생성 → 등록 카드 결제 → 주문 상세 | 11 |
| D. 내 주문 확인 | 10% | 25 | 로그인 → 주문 목록 → 주문 상세 → (5번 중 1번) 환불 요청 | 3.2 (평균) |

#### 비율 근거
- **C 20%:** 결제 README의 "결제 20%" 가정과 같다. 그래서 C의 분당 50회는 새 기준 결제 목표 "세션 분당 50개"(8-2)와 같은 값이 된다
- **채팅 사용(B + C) 50%:** 채팅 견적이 이 서비스의 핵심 기능이라 둘러보기 다음으로 많다고 본다. 견적을 받은 사람(50%) 중 40%가 구매한다(20%)
- **A 40%:** 이커머스에서 가장 많은 행동은 상품 조회라는 일반적인 전환 흐름을 따른다
- **D 10%:** 주문한 사람이 다음 방문에서 배송 상태를 보는 경우
- 비율은 실제 데이터가 아니다. 결과서에 "가정"이라고 쓴다

#### 메시지를 의도별로 섞는 이유
fake LLM에서는 모든 메시지가 견적 요청이었다. 실제 OpenAI에서는 의도마다 LLM 호출 수와 서버 작업이 다르다(5-1).

| 의도 (`MenuPlanIntent`) | LLM 작업 (`LlmOperation`) | 서버 작업 |
|---|---|---|
| 견적 요청 `SHOPPING_REQUEST` | 메뉴 계획 → 견적 안내 | 새 견적 발급 (DB, Redis) |
| 견적 수정 `QUOTE_EDIT` | 메뉴 계획 → 견적 수정 계획 → 견적 안내 | 견적 락, 견적 수정 |
| 리뷰 질문 `LOOKUP_QUESTION` | 메뉴 계획 → 조회 답변 (도구 호출 왕복 포함) | 리뷰 조회 (DB) |
| 일반 질문 `GENERAL_QUESTION` | 메뉴 계획 → 일반 답변 | 메시지 저장만 |

메시지 문장 예시 (스모크에서 의도가 맞게 분류되는지 먼저 확인한다)

| 흐름 | 순서 | 문장 | 기대 의도 | 성공 조건 (k6 check) |
|---|---|---|---|---|
| B | 1 | 김치볶음밥 재료 준비해 줘 | 견적 요청 | `QUOTE_CARD`, 메뉴가 김치볶음밥, 상품 1개 이상 |
| B | 2 | 4인분으로 해 줘 | 견적 요청 (인분 변경은 새 견적, `MenuPlanIntent` 주석) | `QUOTE_CARD`, 새 `quoteId`, 인분이 4 |
| B | 3 | 계란은 빼 줘 | 견적 수정 | `QUOTE_CARD`, 새 `quoteId`, **카드 상품에 계란이 없음**, 나머지 상품은 그대로 |
| B | 4 | 이 김치 리뷰 어때? | 리뷰 질문 | 텍스트 답변, 견적 카드가 바뀌지 않음 |
| B | 5 | 남은 김치볶음밥은 어떻게 보관해? | 일반 질문 | 텍스트 답변, 견적 카드가 바뀌지 않음 |
| C | 1 | 된장찌개 재료 준비해 줘 | 견적 요청 | B 1과 같음 |
| C | 2 | 2인분으로 해 줘 | 견적 요청 | B 2와 같음 |
| C | 3 | 대파는 빼 줘 | 견적 수정 | B 3과 같음 (대파가 없음) |

- **카드가 왔다고 의도대로 처리된 것은 아니다.** 새 견적 발급과 견적 수정 모두 `QUOTE_CARD`를 돌려준다. "계란은 빼 줘"가 새 견적으로 처리돼도 카드는 온다. 그래서 대상 품목이 실제로 빠졌는지까지 본다
- **기대 의도와 실제 처리 의도를 따로 센다.** 실제 의도는 서버 지표 `zelo_chat_reply_seconds`의 `intent` 태그로 센다. k6 check(응답 내용)와 서버의 의도별 건수를 함께 보고, 문장별로 "기대 의도 = 실제 의도" 비율을 결과서에 적는다
- 정확한 payload 필드(인분, 상품 이름)는 사전 확인 응답으로 맞춘다

- 문장은 여러 메뉴(김치볶음밥, 된장찌개, 카레 등)로 돌려 쓴다. 같은 문장만 보내면 상품 후보가 늘 같아 DB 캐시가 실제보다 잘 맞는다
- 리뷰 질문의 상품은 리뷰 시드(`ReviewSeedLoader`)가 있는 상품으로 고른다

#### 도메인 기준선과의 차이
1단계 도메인 기준선은 "그 도메인을 쓰는 사용자 전부가 피크에 몰린다"는 값으로, 그 도메인 요청만 보내서 잰다.

| 도메인 | 기준선 (×1) | 통합 ×1에서 같은 요청 | 차이 |
|---|---|---|---|
| 채팅 | 분당 125세션 (견적을 받는 B + C 50%), 메시지 10.4 RPS | B 75 + C 50 = 분당 125세션, 메시지 8.75 RPS | 세션 수는 같다. 기준선은 세션마다 메시지 5개, 통합은 B 5개·C 3개라 메시지가 적다 |
| 상품 | 41.7 RPS (사용자 1만 명 전부가 10번 부른다고 봄, 상품 README) | A 100 × 9 ÷ 60 = 15 RPS | 기준선이 더 나쁜 경우다 |
| 주문·결제 | 분당 50세션 (구매 20%) | C 분당 50회 | 같다 |
| 환불 | 분당 5회 (환불 2%) | D 25회 중 1/5 = 분당 5회 | 같다 |

### 3-3. ×1에서 예상 트래픽

| 항목 | 계산 | 값 |
|---|---|---|
| 전체 요청 | (100 × 9 + 75 × 8 + 50 × 11 + 25 × 3.2) ÷ 60 | **약 35.5 RPS** |
| 채팅 메시지 | (75 × 5 + 50 × 3) ÷ 60 | **약 8.75 RPS** (분당 525개) |
| LLM 호출 | 5-1 참고 | **분당 약 1,175회** (초당 약 19.6회) |
| 주문 생성 | 50 ÷ 60 | 약 0.83 RPS |
| 결제 요청 (결제수단 조회 + 결제) | 50 × 2 ÷ 60 | 약 1.67 RPS (새 기준 결제 목표 약 1.9 RPS와 비슷) |
| 로그인 | (75 + 50 + 25) ÷ 60 | 약 2.5 RPS |

#### 동시 VU 예상 (리틀의 법칙: VU = 초당 시작 수 × 흐름 하나의 시간)

| 흐름 | 흐름 하나의 시간 (예상) | VU |
|---|---|---|
| A | 요청 9개 + 생각 시간 평균 2초 × 8 ≈ 17초 | 100/60 × 17 ≈ 28 |
| B | 메시지 5개 × 약 12초 + 생각 시간 ≈ 75초 | 75/60 × 75 ≈ 94 |
| C | 메시지 3개 약 40초 + 나머지 약 15초 ≈ 55초 | 50/60 × 55 ≈ 46 |
| D | 약 6초 (생각 시간 포함) | 25/60 × 6 ≈ 2.5 |
| 합계 | | **약 170** |

- 메시지 시간 12초는 로컬 fake(약 10초)보다 길게 잡은 **가정**이다. 실제 OpenAI에서 견적 수정은 LLM을 3번 부르기 때문이다. 실제 10건(1-3)에서는 메시지 하나가 3.4\~6.9초, 견적 수정이 약 10초였다. 사전 확인 실측으로 바꾼다
- 채팅 메시지가 Tomcat 스레드를 잡는 수 = 8.75 RPS × 12초 ≈ 105개로, 200개의 절반쯤이다 (4-3 기준 140개 안쪽)
- 이 값은 k6 VU 설정(`preAllocatedVUs`)의 근거로만 쓴다. 트래픽은 VU 수가 아니라 분당 방문 수로 정한다(`constant-arrival-rate`). 서버가 느려져도 요청이 줄지 않아야 실제 상황과 같기 때문이다

### 3-4. 생각 시간
- 통합 테스트에서는 요청 사이에 1\~3초를 무작위로 쉰다 (`sleep(1 + Math.random() * 2)`). 채팅 메시지 사이에도 같은 값을 넣는다
- 근거: 실제 사용자는 화면을 보고 다음 행동을 한다. 쉬는 시간이 없으면 한 사용자가 서버를 연달아 두드려 동시 세션 수, 토큰 사용 시간, Redis 키 수명이 실제와 달라진다
- 서버에 들어가는 RPS는 바뀌지 않고 동시 VU만 늘어난다 (3-3 표)
- 도메인 기준선은 로컬과 비교하려고 생각 시간 없이 그대로 둔다

### 3-5. 사용자 번호대
시드(`LoadTestUserSeedLoader` 등)가 도메인마다 사용자 번호대를 나눠 두었으므로, 흐름마다 겹치지 않게 쓴다. 겹치면 채팅 메시지 제한(1분 10건)이나 주문 상태 때문에 다른 흐름이 실패한다.

| 흐름 | 사용자 | 로그인 | 근거 |
|---|---|---|---|
| A | 없음 | 없음 | 상품 API는 인증이 필요 없다 |
| B | 5,001\~15,000 | 이메일 | 채팅 시드(`LoadTestChatSeedLoader`)의 방 기록이 있는 사용자 |
| C | 20,001\~25,000 | 소셜 fake (`fake-load-{id}`) | 결제 시드(`LoadTestPaymentSeedLoader`)가 결제수단과 배송지를 넣은 사용자 |
| D | 25,001\~27,000 | 소셜 fake | 환불 시드(`LoadTestRefundSeedLoader`)가 결제 완료 주문을 넣은 사용자 |

- C 사용자는 결제 대기 시드 주문을 이미 가지고 있다. 사전 확인에서 사용자당 대기 주문 제한 같은 규칙에 걸리지 않는지 확인한다. 걸리면 결제 시드 없이 결제수단만 넣는 방법을 결제 담당과 정한다

## 4. SLO (판정 기준)

### 4-1. API별 응답 시간

| 묶음 | API | p95 기준 | 근거 |
|---|---|---|---|
| 입력 중 응답 | 자동완성 | 200ms | 글자를 칠 때마다 부른다. Nielsen의 응답 시간 기준에서 0.1초가 "바로 반응", 1초가 "흐름이 끊기지 않음"이다. 그 사이에서 엄격한 쪽 |
| 조회 | 상품 목록·검색·상세, 인기 상품, 인기 검색어, 카테고리, 방 목록, 메시지 목록, 주문 목록·상세, 배송지, 결제수단 | 500ms | 1초 기준의 절반. 로컬에서 방 목록 p95 0.01초, 결제수단 조회 수십 ms로 여유가 크다 |
| 인증 | 로그인, 소셜 로그인 | 500ms | BCrypt 해시가 CPU를 쓴다. 로컬 부하 p95 0.19초 |
| 쓰기 | 구매 확인, 주문 생성, 환불 요청 | 1초 | 주문 생성은 같은 사용자의 주문 생성을 막는 Redisson 분산락(대기 한도 3초) 안에서 상품마다 재고 행을 DB 행 잠금으로 잡고 차감한다. 분산락 대기 한도가 3초라 그 안에서 충분히 끝나야 한다 |
| 결제 | 등록 카드 결제 | 1.5초 | 포트원 빌링키 결제 실측 p95 1.01초 (README) + 서버 처리 |
| AI | 채팅 메시지 전체 | **20초 (잠정)** | 실제 OpenAI에서 견적 수정은 LLM 3번이다. 메뉴 계획 p95 7.5초 + 나머지 두 호출을 합하면 15초를 넘을 수 있다. 메시지 시간 예산(`time-budget.total`)이 30초라 그보다는 충분히 짧아야 한다. 사전 확인 실측으로 의도별 값을 확정한다 |

- AI 묶음은 의도별(`intent` 태그)로도 따로 적는다. 견적 요청과 일반 질문은 견적 수정보다 짧아야 한다
- 서버 처리 시간(메시지 시간에서 LLM 시간을 뺀 값)은 따로 계산한다 (7장). OpenAI가 느린 것과 우리 서버가 느린 것을 나눠 보기 위해서다

### 4-2. 실패율

| 대상 | 기준 | 비고 |
|---|---|---|
| 전체 요청 | `http_req_failed` < 1% | 5xx와 예상하지 못한 4xx |
| 결제 요청 | < 0.1% | 돈이 걸린 요청이라 더 엄격하게 |
| 채팅 FALLBACK | < 1% | 503(AI_008), 504(AI_002)는 실패 안내라는 정상 응답이지만, 부하 테스트에서 1%를 넘으면 문제로 본다. OpenAI 429 때문인지는 7장 지표로 나눈다 |
| 견적 안내 생략 (DEGRADED) | < 5% | 카드는 저장되지만 안내가 고정 문구다. 지표 `zelo.chat.explain.degraded` (`BusinessMetric.CHAT_EXPLAIN_DEGRADED`) |
| 의도가 기대와 다름 | < 5% | 예: 견적 수정 문장에 일반 답변이 옴, 또는 카드는 왔지만 대상 품목이 빠지지 않음. 서버 실패는 아니지만 C 흐름이 주문까지 가지 못한다. 3-2의 성공 조건 check로 따로 센다 |
| 구매 완료율 (C) | 사전 확인에서 정한 값 이상 | 단계별 도달 건수(9-2 C)로 계산한다. 낮으면 주문·결제 요청이 목표보다 적게 들어간 것이라 주문·결제 결과를 "목표 부하를 처리했다"로 쓰지 않는다 |

### 4-3. 서버 상태

| 항목 | 기준 | 이유 |
|---|---|---|
| Hikari 대기 (`hikaricp_connections_pending`) | 대부분 0, 커넥션 얻는 시간 p95 < 100ms | 대기가 생기면 모든 도메인이 같이 느려진다 |
| Tomcat 바쁜 스레드 | 최대의 70% 미만 (200개 중 140) | 70%를 넘으면 조금만 늘어도 꽉 찬다 |
| 앱 CPU | 평균 70% 미만 | 같은 이유 |
| k6 놓친 방문 (`dropped_iterations`) | 0 | 0이 아니면 k6가 목표만큼 보내지 못한 것이라 결과를 믿을 수 없다 |
| 부하 발생기 CPU | 80% 미만 | 넘으면 측정값에 k6 지연이 섞인다. 로컬에서는 같은 노트북이라 99.8%까지 찼다 |
| 데이터 정합성 | 재고 음수 0, 결제 완료 건수 = k6 결제 성공 수, 중복 주문 0 | 빠르지만 틀리면 통과가 아니다 |

### 4-4. 목표 여유
- **부하 통과:** 통합 ×1에서 위 기준을 모두 지킨다
- **스트레스 목표:** SLO를 지키는 최대 배수가 통합 ×1.5 이상 (채팅 새 기준 결과서의 여유 기준과 같다)
- 근거: 목표에 안전계수 1.5를 이미 넣었다. 새 기준은 예전 기준의 10배라, 예전처럼 ×3을 요구하면 예전 기준의 30배를 버텨야 한다. 로컬 fake에서 채팅 한계가 목표의 약 2배(Tomcat 200)였다. ×1.5에서 못 버티면 4단계에서 고칠 대상으로 삼는다
- 스트레스는 fake LLM으로 하므로 이 배수는 "fake LLM(통합 부하 실측 지연) 기준"이다. 참고로 ×3을 실제 OpenAI로 했다면 RPM의 약 71%(1.2배 여유를 넣으면 85%)를 쓰는 양이다 (5-3)

## 5. 실제 OpenAI 사용 계획

### 5-0. 실제 OpenAI를 부르는 범위
| 테스트 | LLM | 이유 |
|---|---|---|
| 0. 사전 확인 | **실제** | 의도 분류, 토큰 수, AI 오류, 한도 동작을 실제로 봐야 본 테스트를 설계할 수 있다 |
| 1. 채팅 도메인 부하 | **실제** | 채팅만 있는 서버에서 실제 메시지 시간, 서버 처리 시간, AI 오류율을 깨끗하게 잰다 (2장) |
| 1. 그 밖의 도메인 | 쓰지 않음 | 견적은 fake LLM으로 견적 처리만 잰다 (8-2) |
| 2. 통합 부하 (1회) | **실제** | "실제 OpenAI 조건에서 피크 SLO를 지킨다"는 판정은 실제로만 할 수 있다. 여기서 잰 LLM 시간이 3·4단계 fake의 기준이 된다 |
| 3. 통합 스트레스 | fake | 비용 (아래) |
| 4. 고치고 다시 재기: 통합 부하 | **실제** | 고친 뒤에도 "실제 OpenAI 조건에서 피크 SLO를 지킨다"를 같은 조건으로 판정한다. 고치기 전 값은 2단계 결과를 쓴다 |
| 4. 고치고 다시 재기: 통합 스트레스 | fake | 비용 (아래). 고치기 전(3단계)과 같은 fake 설정으로 해서 전·후를 같은 조건으로 비교한다 |

#### 스트레스를 실제 OpenAI로 하지 않는 이유: 비용
5-2와 같은 실측 단가(호출 1회 약 $0.0003)로 계산했다.

| 실제 OpenAI로 하면 | 호출 | 비용 |
|---|---|---|
| 통합 스트레스 1회 (×1\~×3) | 약 40,200 | 약 $11.5 |
| 고치기 전·후 스트레스 2회 (고치기 1건 기준) | 약 80,400 | 약 **$23** |

- 모두 실제 OpenAI로 하면 약 $42.3, 지금 계획은 약 $19.4다. 모두 실제로 했을 때 비용의 약 54%가 스트레스 2회에서 나온다
- 고칠 것이 하나 늘 때마다 지금 계획으로는 통합 부하 1회 약 $7.5가 더 들고, 스트레스까지 실제로 하면 약 $19가 든다
- 스크립트·환경 문제로 다시 돌리면 그 회차 비용이 그대로 한 번 더 든다. 스트레스는 멈춤 조건(10장)을 맞추느라 다시 돌릴 일이 많다
- 비용 말고도 좋아지는 점: 스트레스에서 OpenAI 응답 시간 흔들림이 빠져 한계가 서버 때문인지 가르기 쉽고, 전·후 스트레스의 조건이 같아진다 (11-2)

#### 부하(실제)와 스트레스(fake)의 결과를 같은 기준으로 받기 위한 조치
LLM만 다르고 나머지는 모두 같게 하고, 두 결과가 이어지는지 ×1에서 확인한다.

1. **fake 지연을 통합 부하 실측에 맞춘다.** 통합 부하에서 작업별(`operation`) LLM 시간 분포(`zelo_llm_attempt_seconds`의 p50, p95)를 재서, 그 분포로 fake 지연을 정한다
2. **fake가 실제와 같은 일을 하게 한다.** 지금 `FakeLlmGateway`는 의도가 하나(`zelo.llm.fake.plan-intent`)로 고정이고, 지연도 모든 작업에 같은 범위(`delay`\~`delay-max`) 하나다. 그대로 쓰면 견적 수정(견적 락, 수정 계획)과 리뷰 질문(DB 조회 도구)이 스트레스에서 일어나지 않는다. 그래서 아래 두 가지를 보강한다 (코드 수정이라 채팅 담당이 따로 확인받고 진행한다)
   - 문장별 의도: k6가 보내는 3-2 문장마다 기대 의도를 돌려준다 (예: "빼 줘" → `QUOTE_EDIT`)
   - 작업별 지연: 메뉴 계획, 견적 안내, 견적 수정 계획, 조회 답변, 일반 답변마다 1번의 분포를 따로 준다
   - 보강하지 못하면 스트레스 결과서에 "견적 요청 경로만 포함"이라고 한계로 적는다
3. **LLM 말고는 모두 같게 한다.** 같은 RDS 스냅샷, 같은 인스턴스와 앱 대수, 같은 앱 설정(Hikari, 스케줄러), 같은 k6 스크립트와 문장, 같은 태그(`phase`, `name`, `api`, `intent`), 같은 check
4. **스트레스 ×1 단계로 두 결과를 이어 붙인다.** 스트레스 ×1은 통합 부하와 트래픽이 같다. 아래 값을 두 결과에서 같은 방법으로 뽑아 비교한다. 실제 값은 테스트 뒤 결과서에 "통합 부하(실제) / 스트레스 ×1(fake) / 차이" 세 칸으로 적는다

   | 비교할 값 | 뽑는 곳 | 같다고 보는 기준 (잠정) |
   |---|---|---|
   | 작업별 LLM 시간 p50·p95 | `zelo_llm_attempt_seconds` (operation별), 시작·끝 Prometheus 저장본의 히스토그램 차이 | 작업마다 15% 안. fake 지연을 맞췄는지 보는 값이라 가장 먼저 본다 |
   | 의도별 채팅 메시지 p95 | k6 `http_req_duration{name:sendMessage, intent:...}`, `phase:steady` | 15% 안 |
   | 서버 처리 시간 (메시지 시간 − LLM 시간) | `zelo_chat_reply_seconds` 합계 − `zelo_llm_call_seconds` 합계 ÷ 메시지 수 (7-1) | 차이 0.1초 안. 값 자체가 작아서(로컬 0.17초) 비율 대신 절대값으로 본다 |
   | Tomcat 바쁜 스레드 평균·최대 | `tomcat_threads_busy_threads`, `record-metrics.sh` 5초 간격 | 평균 15% 안 |
   | Hikari 사용 개수, 커넥션 사용 시간 p95 | `hikaricp_connections_active`, `hikaricp_connections_usage_seconds` 히스토그램 차이 | 평균 사용 개수 15% 안, 대기(`pending`)는 둘 다 0 |
   | 채팅이 아닌 API 묶음 p95 (조회, 쓰기, 결제) | k6 `http_req_duration{api:read}`, `{api:write}`, `{kind:payment}`, `phase:steady` | 15% 안, 또는 둘 다 4-1 기준의 절반 아래 |
   | 앱 CPU | CloudWatch EC2 `CPUUtilization` 평균 | 차이 10%p 안 |

   - 모두 기준 안이면 fake가 실제를 흉내 냈다고 보고 ×1.5 이상의 결과를 쓴다
   - LLM 시간이 기준 밖이면 fake 지연을 다시 맞추고 ×1부터 다시 한다
   - LLM 시간은 맞는데 다른 값이 기준 밖이면, fake로 빠진 일(견적 수정 계획·리뷰 조회 도구, 의도 오분류)이 원인인지 의도별 값으로 먼저 나눠 보고 결과서에 적는다
   - 15%, 0.1초, 10%p는 실측 전에 정한 잠정 값이다. 같은 조건 두 번(fake 스트레스 ×1 2회, 11-2의 7번)의 차이가 이보다 크면 그 차이를 기준으로 바꾼다
5. **결과서 형식을 같게 한다.** 부하와 스트레스 결과서는 같은 표(13-2)를 쓰고, LLM 조건 칸에 "실제 OpenAI" 또는 "fake LLM(통합 부하 YYYY-MM-DD 실측 지연)"을 적는다
6. **fake로는 볼 수 없는 것을 적는다.** 높은 배수에서의 OpenAI 한도와 429, 서킷이 열리는 시점, AI 오류율(응답 검증 실패, 의도 오분류)이 부하에 따라 늘어나는지. 실제 AI 오류는 0·1·2단계 결과로만 말한다

### 5-1. 흐름별 LLM 호출 수

| 흐름 | 메시지 | 호출 | 합계 |
|---|---|---|---|
| B | 견적 요청 2 + 인분 변경 2 + 견적 수정 3 + 리뷰 질문 2 + 일반 질문 2 | | **11** |
| C | 견적 요청 2 + 인분 변경 2 + 견적 수정 3 | | **7** |

- ×1 분당 호출 = 75 × 11 + 50 × 7 = **1,175**
- 채팅 기준선(분당 125세션, 모두 B 문장)은 125 × 11 = 분당 **1,375**
- 이 값은 **작업 수**(`zelo.llm.call`) 기준이다. 리뷰 질문은 도구 호출 왕복이 있어 실제 HTTP 요청은 더 많을 수 있고(`zelo.llm.execution.started` 주석), 재시도도 더해진다. 사전 확인에서 두 지표를 같이 보고 계수를 고친다
- 의도 분류가 기대와 다르면 호출 수도 달라진다. 예상 대신 실측을 쓴다

### 5-2. 테스트별 예상 호출 수

| 테스트 | 계산 | 예상 호출 | 예상 비용 (5-4 실측 단가) |
|---|---|---|---|
| 0. 사전 확인 | 채팅 흐름 B 3번, C 3번 (54) + 통합 ×0.1 2분 (약 235) | 약 **290** | 약 $0.1 |
| 1. 채팅 부하 | 분당 125세션 × 11 = 분당 1,375. 데우기 2분(평균 절반) + 유지 10분 = 11분 | 약 **15,100** | 약 $4.3 |
| 2. 통합 부하 (1회) | 분당 1,175 × (데우기 5분 중 실제 2.25분 + 유지 20분) | 약 **26,100** | 약 $7.5 |
| 3. 통합 스트레스 | fake LLM | 0 | $0 |
| 4. 고치고 다시 재기: 통합 부하 (1건) | 2단계와 같음 | 약 **26,100** | 약 $7.5 |
| 4. 고치고 다시 재기: 통합 스트레스 | fake LLM | 0 | $0 |

- 고칠 것이 하나 늘 때마다 통합 부하 1회(약 26,100회, 약 $7.5)가 더 든다
- 다시 돌리면(9-3) 통합 부하 1회 약 $7.5, 채팅 부하 1회 약 $4.3이 더 든다
- 예전 계획(통합 부하 2회, 스트레스·다시 재기도 실제 OpenAI)은 약 20만 회, 약 $57이었다

### 5-3. OpenAI 요청 한도 확인
OpenAI 한도에 먼저 닿으면 429가 나고 그 메시지는 FALLBACK이 되어 우리 서버를 제대로 잴 수 없다.

**계정 한도 (2026-11-05 확인, 조직 Limits 화면)**: RPM **5,000**, TPM **2,000만**. IPM 5만은 이미지 한도라 관계없다.

| 테스트 | 가장 많은 분당 호출 | 필요한 RPM (×1.2 여유) | RPM 5,000 대비 | 필요한 TPM (×1.2 여유) | TPM 2,000만 대비 |
|---|---|---|---|---|---|
| 채팅 부하 | 1,375 | 1,650 | 33% | 약 363만 (1,375 × 2,200 × 1.2) | 18% |
| 통합 부하 | 1,175 | 1,410 | 28% | 약 310만 | 16% |
| (참고) 통합 스트레스 ×3을 실제로 했다면 | 3,525 | 4,230 | 85% | 약 930만 | 47% |

- 실제 OpenAI를 부르는 테스트는 모두 한도의 3분의 1 안쪽이다. 먼저 닿는 쪽은 TPM이 아니라 **RPM**이다
- 이 한도는 **조직 전체가 같이 쓴다.** 테스트 시간에는 같은 조직의 개발·운영 호출을 피하거나 그만큼 여유를 더 둔다. 부하 테스트 전용 프로젝트에 프로젝트 한도를 따로 걸었다면 둘 중 작은 값이 적용된다
- 화면 값과 실제 적용 값이 같은지는 사전 확인에서 응답 헤더(`x-ratelimit-limit-requests`, `x-ratelimit-limit-tokens`)로 확인한다

- 호출당 토큰 2,200은 2026-11-05 실제 메시지 10건(호출 21회)의 평균이다. 입력 약 41,700 + 출력 약 3,700 ÷ 21 ≈ 입력 2,000 + 출력 180
  - 작업별 평균: 메뉴 계획 입력 약 2,750 / 출력 약 205, 견적 안내 약 930 / 47, 견적 수정 계획 약 2,040 / 540
  - 리뷰 질문(조회 답변)과 일반 질문은 아직 재지 않았다. 사전 확인에서 `zelo_llm_tokens_total`(operation, type별)로 잰다
- 호출 수는 작업 수 기준이라, 재시도와 리뷰 질문의 도구 호출 왕복만큼 실제 요청은 더 많다(5-1). 사전 확인에서 `zelo_llm_execution_started_total`로 실제 요청 수를 재서 위 표를 다시 계산한다
- 실행 중 RPM이 한도의 80%(분당 4,000회)에 닿으면 멈추고 "OpenAI 한도"라고 적는다. 지금 계획으로는 닿지 않는다
- 429가 우리 쪽에서 어떤 오류 코드와 FALLBACK으로 집계되는지, 서킷이 열리는지 사전 확인에서 확인한다. 서킷이 열리면 그 뒤 메시지는 LLM을 부르지 않고 바로 FALLBACK이라 결과가 크게 달라진다 (`chat-outage-test-result.md`)

### 5-4. 비용과 승인
- **예상 비용** = Σ(작업별 호출 수 × (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가)). 단가는 실행하는 날의 OpenAI 가격표에서 확인한다
  - 2026-11-05 실측: `gpt-6-luna`(입력 100만 토큰당 $0.10, 출력 $0.50)로 메시지 10건(호출 21회)에 약 $0.006. 메시지 1건에 약 $0.0006, 호출 1회에 약 $0.0003
  - 5-2의 예상 비용은 이 호출당 단가로 계산했다. 리뷰·일반 질문의 토큰 수를 재면 다시 계산한다
- 사전 확인 결과로 1회 비용을 계산해 표로 만들고, **테스트마다 실행 전에 호출 수와 예상 비용을 알리고 승인을 받는다**
- 부하 테스트 전용 OpenAI 프로젝트와 키를 따로 만든다
  - 비용을 운영·개발 사용량과 나눠 볼 수 있다
  - 프로젝트에 사용 한도(예산 알림)를 걸어 스크립트가 잘못 돌아도 정해진 금액을 넘지 않게 한다
  - 테스트가 끝나면 키를 폐기한다
- 키는 EC2 환경변수로만 넘긴다 (SSM Parameter Store 또는 Secrets Manager). 저장소, 스크립트, 결과 파일에 남기지 않는다
- 로그에 프롬프트·응답 전문을 남기지 않는다 (팀 로깅 기준). `performance` 프로필이 `SimpleLoggerAdvisor`를 info로 낮추는지 실행 전에 확인한다

### 5-5. 실제 OpenAI라서 생기는 흔들림
- 같은 요청도 시간대에 따라 OpenAI 응답 시간이 다르다
- 그래서
  - 실행 시각을 결과서에 적는다
  - 실행마다 OpenAI 시간(`zelo_llm_attempt_seconds`, operation별 p50·p95)을 같이 남긴다. 측정 20분을 5분씩 나눠 구간별 값도 남겨, 1회 실행 안에서 흔들림을 본다
  - 흔들림 때문에 원인 비교가 불명확해지는 실험(전·후 비교, 원인 분리 실험)은 같은 AWS 환경에서 통제된 fake 지연으로 먼저 원인을 나누고, 필요하면 실제 OpenAI 조건에서 결과를 한 번 확인한다 (5-0, 7-2)
  - 우리 서버가 좋아졌는지는 LLM 시간을 뺀 서버 처리 시간과 Hikari 히스토그램으로 판단한다 (11-2)

## 6. AWS 테스트 환경

### 6-1. 구성

```
[k6 EC2] ──▶ [ALB] ──▶ [앱 EC2 1~2대] ──▶ [RDS PostgreSQL 16]
   │                         │        ├──▶ [ElastiCache Redis 7]
   │                         │        └──▶ [OpenAI API] (NAT 게이트웨이 경유)
   └── 지표 수집 ────────────┘ (actuator 9292, 보안 그룹으로 k6·모니터링 EC2에만 연다)
```

운영 사양이 정해지면 그 사양을 그대로 쓴다. 정해지지 않았으면 아래 추천값으로 시작한다.

| 구성 | 추천 | 이유 |
|---|---|---|
| 리전 | 운영 예정 리전 하나, 모두 같은 VPC | 리전 간 네트워크 지연을 빼려고. OpenAI까지의 지연은 운영과 같아진다 |
| 부하 발생기 | EC2 4 vCPU (예: c7i.xlarge) 1대 | 로컬 최대 VU가 800 미만이었다. k6는 이 정도면 1대로 충분하다. CPU를 따로 감시한다 |
| 앱 | EC2 2 vCPU / 4\~8GB, **성능이 고정된 타입** (예: m7g.large, c7g.large) | t 시리즈는 CPU 크레딧이 떨어지면 성능이 갑자기 낮아져 결과가 흔들린다 |
| 앱 대수 | 1단계는 1대, 2단계 이후 1대와 2대 둘 다 | 1대에서 병목 원인을 찾기 쉽다. 2대에서는 분산락, 메시지 제한, 멱등성 키가 Redis를 통해 여러 대에서 맞게 동작하는지 본다 |
| RDS | PostgreSQL 16, 2 vCPU 이상, 성능 고정 타입 (예: db.m7g.large), 단일 AZ | t 시리즈는 위와 같은 이유로 피한다 |
| Redis | ElastiCache Redis 7, 작은 노드 (예: cache.t4g.small) | 로컬에서 Redis는 병목이 아니었다 |
| NAT 게이트웨이 | 앱이 프라이빗 서브넷이면 필요 | OpenAI 호출이 나가는 길이다. 처리량과 데이터 요금을 같이 본다 |
| ALB | 운영과 같은 설정 | idle timeout 기본 60초가 채팅의 가장 긴 응답(시간 예산 30초)보다 긴지 확인한다 |
| JVM | 운영과 같은 힙 설정 | |

### 6-2. 앱 설정

| 설정 | 값 | 이유 |
|---|---|---|
| 프로필 | `performance` | SQL, LLM DEBUG 로그를 끈다. 운영도 DEBUG를 켜지 않는다 |

| Hikari | 팀이 정한 AWS 값 (로컬 max 10보다 늘리기로 함. 정해지면 값을 적는다), connection-timeout 30초 | 처음 정한 값으로 잰 결과가 "고치기 전" 기준이 된다. 다시 바꾸는 건 4단계에서. 로컬 새 기준 채팅 스트레스에서는 Tomcat 스레드가 먼저 찼다 (`chat-dau50k-test-result.md`). AWS에서도 그렇다면 커넥션을 늘려도 채팅 한계는 크게 바뀌지 않을 것으로 본다(가설) |

### 6-3. 데이터 상태를 같게 만드는 방법
- 시드를 넣은 뒤 `VACUUM ANALYZE`를 하고 **RDS 스냅샷**을 만든다
- 비교가 필요한 실행(4단계 전·후)은 매번 이 스냅샷에서 새 RDS를 띄워 시작한다
- 이유: 테스트를 돌릴수록 `chat_messages`, `orders`가 늘고 결제 대기 주문이 줄어 다음 실행의 조건이 달라진다. 결제 대기 주문은 생성 30분 뒤 재결제가 막힌다 (README)

## 7. 관측 지표

로컬에서는 `record-metrics.sh`로 5초마다 CSV를 남겼다. AWS에서는 Prometheus가 actuator(9292)를 수집하고 Grafana로 본다. 같은 스크립트를 k6 EC2에서 함께 돌려 CSV도 남긴다(결과서에 넣기 쉽다).

| 층 | 지표 | 보는 이유 |
|---|---|---|
| k6 | API별(`name` 태그) p50·p95·p99, 실패율, `dropped_iterations`, 흐름별(`journey`), 의도별(`intent`) | 판정 기준 |
| 앱 HTTP | `http_server_requests_seconds` (uri별) | k6와 서버 시간의 차이로 네트워크, ALB 대기를 구분 |
| Tomcat | `tomcat_threads_busy_threads` | 스레드 포화. 실제 OpenAI를 기다리는 동안 채팅 요청이 스레드를 잡는다 |
| Hikari | `hikaricp_connections_active`·`pending`, `acquire`·`usage` 히스토그램, `timeout_total` | DB 커넥션 포화. **`_max`는 최근 2\~3분 값이라 전체 최대로 쓰지 않는다** (로컬 결과서 5장) |
| LLM | `zelo_llm_call_seconds`·`zelo_llm_attempt_seconds` (operation, outcome), `zelo_llm_tokens_total` (operation, type), `zelo_llm_execution_started_total`, `zelo_llm_time_budget_exceeded_total`, `resilience4j_circuitbreaker_state` | OpenAI 시간과 실패, 토큰 사용량(비용), 시간 예산, 서킷 |
| 채팅 | `zelo_chat_reply_seconds` (intent, outcome), `zelo_chat_fallback_total` (code), `zelo.chat.explain.degraded`, `zelo.chat.quote.busy`, `zelo.chat.rate.limited` | 의도별 처리 시간, FALLBACK 원인, 견적 락 대기 |
| 업무 | `zelo_api_error_total{code}`, `zelo_payment_result_total{status}` | 실패 원인 |
| 인프라 | CloudWatch: EC2 CPU, ALB `TargetResponseTime`·`HTTPCode_Target_5XX`, RDS `CPUUtilization`·`DatabaseConnections`, NAT 게이트웨이 처리량 | 앱 밖의 병목 |
| DB 쿼리 | RDS Performance Insights (상위 SQL, 대기 이벤트) | 느린 쿼리와 락 대기를 SQL 단위로 찾는다 |
| OpenAI 사용량 | OpenAI 대시보드의 부하 테스트 프로젝트 사용량 | 앱 지표의 토큰 수와 맞는지 확인 |

### 7-1. 분석 규칙 (로컬에서 틀렸던 것)
- 단계별 집계는 k6 CSV의 `timestamp`(요청이 **끝난** 시각)가 아니라 **보낸 시각 = timestamp − duration**으로 나눈다. 끝난 시각으로 나눴을 때 스트레스 ×3 p95가 34.2초가 아니라 23.7초로 잘못 나왔다
- 시작과 끝에 `/actuator/prometheus` 전체를 파일로 저장한다. 누적 히스토그램 차이로 테스트 동안의 정확한 건수를 계산할 수 있다
- **서버 처리 시간 = 채팅 메시지 시간 − 그 메시지의 LLM 시간.** 메시지 단위로는 로그의 traceId로 맞추고, 전체로는 `zelo_chat_reply_seconds` 합계 − `zelo_llm_call_seconds` 합계를 메시지 수로 나눠 평균을 본다

### 7-2. 원인까지 좁히는 방법
위 지표로 **어떤 기능이 느려졌는지, 어떤 자원이 찼는지**는 상당 부분 알 수 있다. 하지만 아래 두 문장은 증거 수준이 다르다.

- "주문 생성이 느리고 DB 대기가 많았다."
- "주문 생성 중 특정 재고 조회가 행 잠금을 기다리면서 느려졌다."

두 번째까지 말하려면 아래 단계가 끊기지 않고 이어져야 한다. 결과서의 원인 문장은 몇 단계까지 확인했는지 함께 적는다.

| 확인 단계 | 필요한 기록 | 이 계획에서 쓰는 것 |
|---|---|---|
| 어떤 API가 느린가 | API별 응답 시간·실패율 | k6 `name` 태그, `http_server_requests_seconds` (7-1) |
| 어떤 요청을 조사할까 | 느린 요청의 `X-Trace-Id` | 응답 헤더 `X-Trace-Id`(`TraceIdResponseFilter`). k6에서 기준을 넘은 요청과 실패한 요청의 traceId를 VU마다 처음 몇 건만 로그로 남긴다 |
| 요청 내부 어디가 느린가 | 락 대기·재고 조회·외부 호출·저장 구간 시간 | 채팅은 LLM 시간(`zelo_llm_call_seconds`)과 서버 처리 시간이 이미 있다. 나머지는 아래 "추가할 내부 측정" |
| 왜 그 구간이 느린가 | DB 대기 이벤트·SQL·로그 | RDS Performance Insights(대기 이벤트, 상위 SQL), traceId로 모은 그 요청의 로그 |
| 정말 그 원인인가 | 한 조건만 바꾼 비교 실험 | 아래 "원인 확인 실험", 4단계 전·후 비교 (11-2) |

#### 추가할 내부 측정 (많지 않다)
지금 지표로 나뉘지 않는 구간만 시간을 잰다. 이름은 `BusinessMetric` enum에 추가하고, 태그는 결과·에러 코드처럼 값이 정해진 것만 쓴다 (팀 지표 기준). 각 도메인 담당이 넣는다.

| 도메인 | 잴 구간 |
|---|---|
| 주문 | 분산락 대기(`LockKey.createOrder`), 재고 조회·잠금(`findInventoryByProduct_Id`), 주문 저장 |
| 결제·환불 | 락 대기, 외부 호출(포트원, fake 지연 포함), 결과 저장 |
| 채팅 | 기존 지표로 나뉘지 않는 구간: 견적 수정(견적 락 대기 포함), 리뷰 도구 조회 |

#### 원인 확인 실험
지표가 같이 움직인다는 것만으로는 원인이라고 말할 수 없다. 의심하는 조건 하나만 바꾸고 나머지는 고정한 실험으로 확인한다.

- 예: **채팅이 다른 기능을 느리게 하는지** 확인하려면 상품 조회량은 고정하고 채팅량만 늘린다. 상품 조회 지연이 함께 늘고, 요청 스레드 대기(Tomcat 바쁜 스레드가 최대에 닿음)가 늘어나는 것이 확인되면 기능 간 영향에 대한 설명이 훨씬 강해진다
- 실험은 3단계 스트레스와 같은 fake LLM 환경에서 한다. 실제 AI 변동이 없어 바꾼 조건의 효과만 남는다. 실제 AI 조건에서도 같은지 확인이 필요하면, 원인을 나눈 뒤 실제 OpenAI로 짧게 한 번 확인한다 (승인 후)

## 8. 1단계: 도메인별 부하·스트레스

### 8-1. 공통 방법
1. 사전 확인 (VU 1\~3, 1\~2분): 기준 응답 시간을 잰다
2. 부하: 도메인 목표 ×1을 10분
3. 스트레스: ×1부터 무너질 때까지 단계적으로 올린다. 단계마다 3분 이상 유지 (로컬 채팅은 80초라 단계 사이에 섞이는 구간이 컸다)

- 같은 AWS 환경에서 두 도메인을 동시에 돌리지 않는다. 결과가 섞인다

### 8-3. 1단계 완료 기준
- 도메인마다 "×몇에서 무엇이 막혔는지"를 한 줄로 적을 수 있다
- 채팅은 "실제 OpenAI에서 의도별 메시지 p95, 서버 처리 시간, Tomcat 점유"를 로컬 fake 결과와 비교한 표가 있다
- 로컬과 AWS 수치가 다르면 이유(CPU 분리, 네트워크, 실제 LLM)를 적는다

## 9. 2단계: 통합 부하

### 9-1. 스크립트 구조
`load-test/integrated/` 아래에 둔다. 흐름마다 함수 하나, 시나리오 하나다.

```js
// load-test/integrated/integrated-load.js (구조 예시)
import { browse } from './journeys/browse.js';
import { quoteChat } from './journeys/quote-chat.js';
import { purchase } from './journeys/purchase.js';
import { myOrders } from './journeys/my-orders.js';

const VISITS_PER_MINUTE = 250 * Number(__ENV.MULTIPLIER || 1);
const SHARE = { browse: 0.4, quoteChat: 0.3, purchase: 0.2, myOrders: 0.1 };

// arrival-rate의 target은 정수만 받는다 (예: 250 × 0.1 × 0.5 = 12.5는 오류)
function rate(name, ratio) {
    return Math.round(VISITS_PER_MINUTE * SHARE[name] * ratio);
}

// 데우기 5분은 판정에서 뺀다. 데우기와 측정을 시나리오로 나누고 phase 태그를 붙여, 기준은 phase:steady에만 건다
const WARMUP = '5m';
const STEADY = '20m';
// 측정이 끝난 뒤 진행 중인 방문을 기다리는 시간. B(약 75초)가 가장 길어 그보다 길게 잡는다
const GRACEFUL_STOP = '120s';

// VU는 3-3의 예상 VU(A 28, B 94, C 46, D 2.5)에 여유를 둔다
const VUS = { browse: [40, 100], quoteChat: [140, 400], purchase: [70, 200], myOrders: [5, 20] };

function warmup(name) {
    return {
        executor: 'ramping-arrival-rate',
        startRate: 0,
        timeUnit: '1m',
        // 3분 동안 절반까지 올리고, 2분 동안 목표까지 올린다
        stages: [
            { duration: '3m', target: rate(name, 0.5) },
            { duration: '2m', target: rate(name, 1) },
        ],
        preAllocatedVUs: VUS[name][0],
        maxVUs: VUS[name][1],
        // 데우기가 끝날 때 진행 중인 방문은 끊지 않고 마저 끝낸다 (끝난 요청은 phase:warmup으로 남는다)
        gracefulStop: GRACEFUL_STOP,
        exec: name,
        tags: { journey: name, phase: 'warmup' },
    };
}

function steady(name) {
    return {
        executor: 'constant-arrival-rate',
        rate: rate(name, 1),
        timeUnit: '1m',
        startTime: WARMUP,
        duration: STEADY,
        preAllocatedVUs: VUS[name][0],
        maxVUs: VUS[name][1],
        gracefulStop: GRACEFUL_STOP,
        exec: name,
        tags: { journey: name, phase: 'steady' },
    };
}

export const options = {
    scenarios: Object.fromEntries(Object.keys(SHARE).flatMap((name) => [
        [`${name}Warmup`, warmup(name)],
        [`${name}Steady`, steady(name)],
    ])),
    thresholds: {
        'http_req_failed{phase:steady}': ['rate<0.01'],
        'http_req_failed{phase:steady,kind:payment}': ['rate<0.001'],
        'http_req_duration{phase:steady,name:autocomplete}': ['p(95)<200'],
        'http_req_duration{phase:steady,api:read}': ['p(95)<500'],
        'http_req_duration{phase:steady,name:login}': ['p(95)<500'],
        'http_req_duration{phase:steady,api:write}': ['p(95)<1000'],
        'http_req_duration{phase:steady,kind:payment}': ['p(95)<1500'],
        'http_req_duration{phase:steady,api:ai}': ['p(95)<20000'],
        'checks{phase:steady,check:기대한 의도}': ['rate>0.95'],
        'dropped_iterations{phase:steady}': ['count==0'],
    },
};

export { browse, quoteChat, purchase, myOrders };
```

- 요청마다 `name`(API), `api`(read, write, ai. k6가 `group` 태그를 이미 쓰므로 다른 이름), 결제 요청은 `kind:payment`, 채팅 메시지는 `intent`(기대 의도) 태그를 붙인다. 섞어서 보내도 API별, 의도별로 나눠 볼 수 있다
- 기준(threshold)은 **데우는 5분을 빼고** 판정한다. 위처럼 데우기·측정 시나리오에 `phase` 태그를 붙이고 기준을 `phase:steady`에만 건다. k6가 출력하는 이 값이 공식 판정이다
  - 데우기 시나리오가 끝날 때 진행 중이던 방문은 `gracefulStop` 동안 마저 끝나므로, 측정 구간 처음 약 2분에는 `phase:warmup` 요청이 섞여 서버 부하가 목표보다 조금 높다. 서버 지표는 측정 시작 2분 뒤부터 본다
  - CSV에서 보낸 시각(7장)으로 다시 계산한 값은 확인용으로만 쓴다
- **방문(세션)을 상태별로 센다.** 진행 중이던 방문이 끝에 잘리면 그만큼 요청이 빠지기 때문이다 (로컬 채팅 스트레스에서도 끝날 때 마치지 못한 세션이 있었다)

  | 상태 | 세는 방법 |
  |---|---|
  | 시작한 방문 | 흐름 함수 첫 줄에서 `Counter` `visit{state:started}` +1 |
  | 정상 완료 | 흐름 마지막 요청까지 성공하면 `visit{state:completed}` +1 |
  | 오류로 중단 | 중간 요청이 실패해 `return`할 때 `visit{state:aborted, step:...}` +1 |
  | 시작하지 못함 | k6 `dropped_iterations` (VU가 모자라 보내지 못한 방문) |
  | 테스트 종료로 중단 | k6 출력의 `interrupted` 반복 수. 확인용으로 started − completed − aborted와 맞춰 본다 |

  - 종료 유예시간은 `gracefulStop: 120s`다. 측정 20분이 끝나면 새 방문은 시작하지 않고, 진행 중인 방문만 120초까지 기다린다
  - 새 방문이 멈춘 뒤 서버에 남은 작업이 0으로 내려가는지 본다: `zelo_chat_inflight`, `tomcat_threads_busy_threads`, `hikaricp_connections_active`. 0이 되기까지 걸린 시간도 결과서에 적는다
- 로그인은 방문마다 한다. 토큰을 setup에서 미리 받아 두면 access 토큰이 10분 뒤 만료되고(`jwt.access-expiration`), 실제처럼 로그인 비용도 들어가지 않는다
- 채팅 응답은 의도에 따라 payload가 다르다. 견적 요청·수정은 `QUOTE_CARD`, 리뷰·일반 질문은 텍스트 답변을 기대 의도 check로 확인한다. 정확한 payload 타입은 사전 확인 응답으로 맞춘다

- **구매 단계별 도달 건수를 따로 센다.** k6 `Counter` `purchase_step`에 `step` 태그를 붙여 단계마다 1씩 더한다

  | 단계 (`step`) | 세는 시점 |
  |---|---|
  | `started` | 로그인 성공 |
  | `quote_ready` | 3번 성공 조건을 지킨 견적 카드를 받음 |
  | `order_tried` / `order_ok` | 8번 요청 전 / 8번 201 |
  | `payment_tried` / `payment_ok` | 9번 요청 전 / 9번 결제 성공 |
  | `completed` | 10번 주문 상세에서 결제 완료 상태 확인 |

  - 예: 구매 1,000건이 시작됐는데 결제 요청이 600건이면 "결제 600건을 잘 처리했다"와 "목표 구매 부하를 처리했다"는 다른 결론이다. 결과서에는 단계별 건수와 단계 사이 비율을 같이 적는다
  - 통합 C는 그대로 두고, 주문·결제가 목표 요청량을 실제로 받는지는 1단계 주문·결제 **단독** 테스트(8-2)로 확인한다. 단독 테스트는 시드 견적·시드 주문으로 시작해 앞 단계 실패에 영향받지 않는다
- 견적은 Redis에서 10분 뒤 만료되므로 3\~8번이 10분 안에 끝나야 한다. 생각 시간을 넣어도 1분 안쪽이라 문제없다
- 요청 본문은 `http/zelo-scenario.http`와 각 Request DTO에 맞춘다

### 9-3. 실행 방법
1. 스냅샷에서 RDS 시작 → 앱 시작 (스케줄러 켬)
2. 사전 확인 (`MULTIPLIER=0.1`, 2분): 토큰 수, 오류 없음, 그리고 **B·C가 끝까지 완료되는지** 확인한다
   - B: 메시지 5개가 모두 3-2의 성공 조건을 지킨다 (기대 의도 = 실제 의도, 견적 수정은 대상 품목이 빠짐)
   - C: 구매 단계별 도달 건수(9-2 C)에서 시작한 방문이 결제 성공까지 간다3. 호출 수와 예상 비용을 알리고 승인을 받는다 (5-4)
4. 시작 전 Prometheus 전체 저장
5. `record-metrics.sh`와 k6를 함께 실행 (데우기 5분 + 유지 20분)
6. 끝난 뒤 Prometheus 전체 저장, DB 정합성 쿼리 실행 (재고 음수, 결제 완료 건수, 중복 주문), OpenAI 사용량 확인
7. **1회만 한다.** 기준을 여유 있게 통과하면 끝낸다. 아래 경우에만 한 번 더 돌린다 (앱 재시작, 같은 스냅샷, 약 $7.5 추가, 실행 전 승인)

   | 다시 돌리는 경우 | 이유 |
   |---|---|
   | 판정이 아슬아슬함 (p95가 기준의 90% 이상, 실패율 0.8% 이상 등) | 한 번 더 하면 통과·실패가 뒤집힐 수 있다 |
   | 실행 중 OpenAI 쪽 이상 (429, 서킷 열림, LLM p95가 사전 확인보다 크게 김) | 우리 서버가 아니라 그날 OpenAI 상태가 결과를 정했을 수 있다 |
   | 측정이 무효 (`dropped_iterations` > 0, 부하 발생기 CPU 80% 초과, 스크립트 오류) | 측정 자체를 믿을 수 없다 |

8. 끝난 뒤 작업별 LLM 시간 분포를 뽑아 3·4단계 fake 지연 값으로 넘긴다 (5-0)

### 9-4. 유지 시간을 20분으로 한 이유
- 스케줄러(배송 60초, 결제 대조 60초, 주문 만료 30초)가 여러 번 돈다
- 로컬 채팅 부하에서 230\~260초 구간에 Hikari가 꽉 찬 일이 있었다. 몇 분짜리 테스트에서는 이런 일시적인 현상이 우연인지 반복되는지 구분할 수 없다
- 30분 대신 20분으로 줄인 것은 실제 OpenAI 호출 수 때문이다. 10분 줄이면 1회에 약 11,750회(약 $3.4)가 준다
- **토큰·견적 만료 경로는 이 테스트로 검증하지 않는다.** 방문마다 새로 로그인하고 새 견적을 1분 안팎에 쓰므로, 테스트가 20분이어도 만료된 access 토큰(10분)이나 만료된 견적(10분)을 쓰는 행동은 생기지 않는다. 이번 범위에 넣지 않았고, 필요하면 만료된 값을 일부러 쓰는 흐름을 따로 만든다

### 9-5. 통합에서만 볼 수 있는 것 (결과서에 꼭 넣는다)
1. 채팅 메시지가 몰리는 순간(실제 OpenAI가 느린 순간)에 상품 조회 p95가 같이 오르는지 (시간대별로 겹쳐 그린다)
2. 스케줄러가 도는 순간에 주문, 결제 p95가 튀는지
3. 앱 1대와 2대의 차이: 처리량이 2배 가까이 늘어나는지, 아니면 RDS, Redis, OpenAI 한도에서 막히는지

## 10. 3단계: 통합 스트레스

| 항목 | 값 | 이유 |
|---|---|---|
| LLM | **fake** (통합 부하 실측 지연, 문장별 의도) | 비용 (5-0). 실제 OpenAI로 하면 약 40,200회, 약 $11.5 |
| 배수 | ×1, 1.5, 2, 2.5, 3 | 로컬 새 기준 채팅 한계가 메시지 약 20 RPS(Tomcat 200, fake 메시지 약 9.7초)였다. 통합 ×k에서 메시지는 8.75k RPS라, 스레드가 먼저 차고 메시지 시간이 fake와 같다고 가정하면 ×2.3 근처에서 Tomcat이 찬다(가설). 실제 메시지가 더 짧으면 더 위에서 막히고, 다른 자원이 먼저 차면 더 아래에서 막힌다. ×3이면 그 너머도 볼 수 있다. fake라 OpenAI 비용이 없으므로 ×3에서도 막히지 않으면 ×4를 더한다 |
| ×1 단계 | 통합 부하와 비교 | 5-0의 비교표로 fake가 실제를 흉내 냈는지 확인한다. 차이가 크면 멈추고 fake 지연을 다시 맞춘다 |
| 단계 길이 | 올리기 30초 + 유지 3분 | 메시지 하나가 20초 안쪽이라 3분이면 단계마다 메시지가 충분히 쌓인다. 분석에서는 각 단계의 처음 30초를 뺀다 |
| 총 길이 | 약 18분 | |
| 멈춤 조건 | 실패율 10% 초과 또는 p95가 기준의 5배를 넘는 상태가 2분 계속 | 그 뒤는 볼 것이 적다. k6 `abortOnFail` + `delayAbortEval: '2m'` |
| 원인 확인 실험 | 7-2 | 스트레스에서 의심되는 원인이 나오면 같은 fake 환경에서 그 조건 하나만 바꿔 확인한다 (예: 상품 조회량 고정, 채팅량만 증가) |

### 기록할 것 (단계별, 보낸 시각 기준)
- API 묶음별 p95, 실패율, 실제 처리량(초당 성공 메시지, 주문)
- 의도별 메시지 p95, 서버 처리 시간 (메시지 시간 − LLM 시간)
- fake LLM 시간(operation별 p95. 설정한 분포대로 나왔는지 확인용), 서킷 상태
- Tomcat, Hikari, 앱 CPU, RDS CPU 중 **가장 먼저 한계에 닿은 것**. OpenAI 한도는 fake라 볼 수 없으므로, 그 배수의 분당 호출을 계산해 5-3 한도와 비교한 값을 따로 적는다
- 원인 문장은 7-2 표의 몇 단계까지 확인했는지 함께 적는다
- 실패 코드 분포 (`zelo_api_error_total{code}`, `zelo_chat_fallback_total{code}`)
- 결과 한 줄 예: "×2.5에서 Tomcat 스레드 200개가 채팅 요청으로 차며 상품 조회 p95가 0.05초에서 2.1초로 올랐다. 원인은 LLM을 기다리는 동안 스레드를 잡는 채팅 요청"

## 11. 4단계: 고치고 다시 재기

### 11-1. 고칠 후보 (지금까지 찾은 것)

| 후보 | 담당 | 근거 | 기대 효과 |
|---|---|---|---|
| 견적 발급이 DB 커넥션을 오래 잡는 구간 줄이기 **(#411에서 고침)** | 견적 담당 | 로컬에서 커넥션 1개를 1.1\~2.5초 사용, ×3에서 대기 평균 5.04초. 수정 뒤 로컬 채팅 부하의 커넥션 대여 1회 평균 40ms(모든 대여의 평균), 로컬 채팅 한계 메시지 3.8 → 20 RPS | AWS에서는 전·후 비교 대상이 아니다. 고친 코드로 잰다 |
| `connection-timeout` 30초 → 더 짧게 | 팀 | 30초 동안 기다린 뒤 500이 난다. 그동안 Tomcat 스레드도 잡혀 있다 | 막힐 때 빨리 실패해 스레드를 돌려준다 |
| Hikari 풀 크기 | 팀 | 지금 10. HikariCP 문서는 `(DB CPU 코어 수 × 2) + 디스크 수`에서 시작하라고 한다 | AWS 사양에 맞는 값. 앱 2대면 RDS 커넥션 수 한도도 함께 본다 |
| 채팅 동시 처리 제한 (Bulkhead) | 채팅 | 새 기준 로컬 채팅 스트레스 ×2.5에서 Tomcat 200개가 채팅 요청으로 찼다. 실제 OpenAI 응답이 길면 더 빨리 찬다 | 채팅이 몰려도 다른 API 스레드가 남는다 |
| LLM을 기다리는 동안 스레드를 잡지 않게 하기 (가상 스레드 `spring.threads.virtual.enabled`, 비동기 응답) | 채팅 | 위와 같다. 로컬에서는 LLM을 기다리는 채팅 요청이 스레드를 잡아 Tomcat 200이 찼다 | 요청 스레드 포화가 병목이라면 한계가 다른 자원으로 옮겨 간다. 후보는 DB 커넥션, CPU, OpenAI 한도다. DB 커넥션 쪽 약 55 RPS는 검증한 최대치가 아니다. 로컬 저부하에서 잰 메시지당 커넥션 사용(4.6회 × 40ms)이 고부하에서도 그대로라고 가정한 추정이다. Java 21에서 `synchronized` 안에서 기다리는 코드는 스레드를 놓지 못하므로 확인한다 |

### 11-2. 다시 잴 때 지킬 것

1. **한 번에 하나만 바꾼다.** 코드 수정과 풀 크기 변경을 같이 하면 어느 쪽 효과인지 알 수 없다
2. **조건을 같게 한다**
   - 같은 RDS 스냅샷, 같은 인스턴스 타입, 같은 시드, 같은 k6 스크립트와 버전, 같은 앱 설정, 같은 OpenAI 모델과 프롬프트
   - 결과서에 커밋 해시와 바꾼 것 하나를 적는다
   - 프롬프트(`src/main/resources/prompts`)가 바뀌면 토큰 수와 LLM 시간이 바뀌므로, 전·후 사이에 프롬프트를 바꾸지 않는다
3. **데우는 방식도 같게 한다.** 첫 실행은 DB 버퍼 캐시가 비어 있어 느리다. 전·후 모두 앱 재시작 → 데우기 5분 → 측정으로 맞춘다
4. **LLM 조건을 테스트마다 전·후 같게 한다.**
   - 통합 부하: 전·후 모두 **실제 OpenAI** 1회. 고치기 전 값은 2단계 결과를 쓴다 (고친 뒤 1회 약 $7.5, 실행 전 승인)
   - 통합 스트레스: 전·후 모두 **같은 fake 설정**(3단계에서 쓴 지연·의도 값 그대로). 고친 뒤 통합 부하에서 LLM 시간이 달라졌어도 fake 값은 바꾸지 않는다. 바꾸면 LLM 조건과 고친 것의 효과가 섞인다
5. **OpenAI 흔들림을 분리한다.** 통합 부하는 실제 OpenAI라 전·후의 응답 시간이 시간대마다 흔들린다
   - 전·후를 비슷한 시간대에 잰다
   - 전·후의 OpenAI 시간(operation별 p50·p95)을 표에 같이 적는다. 이 값이 크게 다르면 메시지 전체 시간 비교는 참고로만 쓴다
   - 우리 서버가 좋아졌는지는 **LLM에 영향받지 않는 값**으로 판단한다: 서버 처리 시간, 커넥션 사용·대기 시간 히스토그램, 채팅이 아닌 API의 p95. 한계(SLO를 지킨 최대 배수)는 fake 스트레스 전·후로 판단한다
6. **같은 지표로 비교한다.** 전·후 표에는 같은 API의 p95, 같은 단계의 처리량, 같은 히스토그램을 쓴다. `_max`는 쓰지 않는다
7. **흔들림 폭을 알고 비교한다.** fake 스트레스 ×1을 전·후 각각 2번 이상 잰다(OpenAI 비용 없음). 전·후 차이가 같은 조건 두 번의 차이보다 작으면 "차이 없음"으로 적는다. 실제 통합 부하는 1회라 이 판정에 쓰지 않고, 기준(4장)을 지키는지만 본다
8. **병목이 옮겨 갔는지 본다.** DB 대기가 사라져도 CPU, Tomcat, OpenAI 한도에서 다시 막힐 수 있다. 처리량 한계가 얼마나 올랐는지와 새 병목을 같이 적는다
9. **정합성을 다시 확인한다.** 빨라지게 고치다가 락 범위를 줄이면 재고가 음수가 되거나 중복 주문이 생길 수 있다. 4-3의 정합성 쿼리를 매번 돌린다
10. **로컬과 AWS 수치를 섞어서 비교하지 않는다.** 전·후 비교는 같은 환경 안에서만 한다
11. 개선 전 결과 파일은 지우지 않고 `before/`, `after/`로 나눠 남긴다

## 12. 일정

| 날 | 할 일 | 실제 OpenAI |
|---|---|---|
| 0일 (로컬) | 통합 스크립트 작성, fake LLM으로 로컬 스모크까지 | 없음 |
| 1일 | 환경 구성, 시드, 스냅샷, 사전 확인 (토큰 수, 의도 분류, OpenAI 한도), 예상 비용 계산 | 약 290회 |
| 2일 | 1단계 도메인별 부하·스트레스 (도메인 담당별로 나눠 실행) | 채팅 부하 약 15,100회 |
| 3일 | 2단계 통합 부하 1회 (실제), fake 지연 맞추기, 3단계 통합 스트레스 (fake), 원인 확인 실험 (fake) | 통합 부하 약 26,100회 |
| 4일 (로컬) | 고치기 | 없음. AWS 리소스는 내려 둔다 |
| 5일 | 4단계 다시 재기: 통합 부하 1회 (실제), 통합 스트레스 (fake, 3단계와 같은 설정) | 통합 부하 약 26,100회 |

- fake 보강(문장별 의도, 작업별 지연)과 내부 측정 추가(7-2)는 0일 로컬 작업에 넣는다

- AWS 리소스는 테스트하는 날에만 띄우고, 끝나면 RDS 스냅샷만 남기고 삭제한다
- 시작 전 예상 비용을 AWS 요금 계산기와 OpenAI 가격표로 확인하고, AWS Budgets와 OpenAI 프로젝트 사용 한도를 걸어 둔다
- AWS의 부하 테스트 정책(Simulated Events)에서 사전 신청이 필요한 규모인지 확인한다. 이 계획의 규모(통합 ×1 약 35.5 RPS, ×3 약 107 RPS)는 작지만 직접 확인한다

### 13-2. 결과서마다 넣을 것
1. 환경 표: 커밋 해시, 인스턴스 타입, 앱 대수, Hikari·Tomcat 설정, 시드 건수, k6 버전, 실행 시각, OpenAI 모델
2. 가정 표: DAU, 피크 비율, 흐름 비율, 메시지 문장 (3장)
3. k6 결과: API별·의도별 p95·p99, 실패율, 처리량, 방문 상태별 건수(시작, 완료, 오류 중단, 시작 못 함, 종료로 중단), C 구매 단계별 도달 건수, 문장별 기대 의도 = 실제 의도 비율 (모두 `phase:steady` 기준)
4. LLM: operation별 시간, 호출 수, 토큰 수, 429, FALLBACK, 실제 비용
5. 서버 상태: 단계별 Tomcat, Hikari, CPU, RDS
6. 판정: SLO 표에 통과·실패 표시
7. 알게 된 것: 수치로 설명할 수 있는 사실만 적고, 원인을 모르는 것은 "원인 확인 못 함"으로 적는다
8. 원본 파일 목록: k6 summary JSON, CSV, `record-metrics` CSV, Prometheus 시작·끝 전체. 프롬프트·응답 전문과 키는 넣지 않는다

### 13-3. 포트폴리오에 쓸 수치 (예상 목록)
- "DAU 5만 가정 피크의 1.5배(분당 방문 250회, 실제 OpenAI 분당 약 1,175회)에서 모든 API가 SLO를 지켰다"
- "통합 스트레스(실측 지연을 넣은 fake LLM)에서 ×N에서 처음 막혔고, 원인은 X였다"
- "X를 고쳐 SLO를 지키는 최대 배수가 ×N에서 ×M으로 올랐다"
- "실제 OpenAI를 기다리는 동안에도 DB 커넥션을 잡지 않아, 채팅이 몰려도 상품 조회 p95는 Y였다"
- "테스트 전체 OpenAI 비용 Z원, 메시지 1건당 W원"

## 14. 위험과 한계

| 항목 | 내용 | 대응 |
|---|---|---|
| 비율과 DAU가 가정 | 실제 사용 데이터가 없다 | 결과서에 가정이라고 적는다 |
| OpenAI 응답 시간의 흔들림 | 시간대와 OpenAI 상태에 따라 같은 테스트도 결과가 다르다. 통합 부하는 1회만 한다 | 실행 시각과 구간별 LLM 시간을 함께 적고, 다시 돌리는 조건(9-3)을 정해 두었다. 전·후 비교는 fake로 한다 (11-2) |
| OpenAI 요청 한도 | 계정 RPM 5,000, TPM 2,000만. 실제로 부르는 테스트는 RPM의 33% 이하다. 조직 전체가 같이 쓴다 | 테스트 시간에 다른 호출을 피하고, 사전 확인에서 응답 헤더로 실제 한도를 확인한다 (5-3) |
| 비용 | 실제 OpenAI 약 67,600회, 약 $19 (고치기 1건, 실측 단가 기준) | 전용 프로젝트·키, 사용 한도, 테스트마다 승인 (5-4) |
| 스트레스가 fake | 실제 OpenAI의 높은 부하에서의 지연, 429, AI 오류 증가를 볼 수 없다 | 통합 부하 실측으로 fake를 맞추고 ×1에서 두 결과를 비교한다 (5-0). 결과서에 "fake LLM 기준"이라고 적는다 |
| fake가 실제 흐름을 다 흉내 내지 못함 | 지금 fake는 의도 하나·지연 하나다 | 문장별 의도·작업별 지연을 보강한다. 못 하면 "견적 요청 경로만 포함"이라고 적는다 (5-0) |
| 예전 기준으로 잰 도메인 | 결제·주문·환불의 로컬 결과는 예전 기준(목표의 1/10)이다 | AWS 전에 새 목표로 다시 잰다 (8-2) |
| 의도 분류가 기대와 다름 | 실제 LLM이라 같은 문장도 다르게 분류될 수 있다. 그러면 C 흐름이 주문까지 가지 못하고 주문·결제 트래픽이 줄어든다 | "기대한 의도" check로 비율을 세고, 5%를 넘으면 문장을 고친 뒤 다시 한다 |
| 서킷이 열리면 결과가 바뀜 | 429나 시간 초과가 몰리면 서킷이 열려 메시지가 바로 FALLBACK이 되고 서버 부하가 갑자기 줄어든다 | 서킷 상태를 단계별로 기록하고, 열린 구간은 따로 표시한다 |
| 다른 외부 서비스는 fake | 포트원, 소셜 로그인의 실제 변동이 없다 | 지연 값은 실측으로 맞추고, 결과서에 fake라고 적는다 |
| 시드 데이터 분포 | 시드 주문과 방은 실제보다 고르게 퍼져 있다 | 인기 상품 몰림은 8-2 주문 ②로 따로 잰다 |
| 로컬 결과와 다름 | CPU, 디스크, 네트워크, LLM이 다르다 | 로컬 결과는 "같은 경향인지"만 보고 숫자는 AWS 결과를 쓴다 |
