# 채팅 부하 테스트 결과 (스모크 · 부하 · 스트레스)

- 실행일: 2026-11-04
- 브랜치: `feat/393-chat-seed`
- 확인하려는 것: **AI 응답을 기다리는 동안 DB 커넥션을 붙잡지 않는가**, 트래픽을 올리면 어디서 처음 무너지는가
- 결과
  - 스모크·부하 모두 통과했다. AI를 기다리는 동안 DB 커넥션을 붙잡지 않았다 (스트레스에서도 같았다).
  - 스트레스에서는 목표의 3배(메시지 6.3 RPS)부터 응답이 2배로 느려졌고, 6배부터 실패가 났다. 처음 막힌 곳은 견적 발급이 쓰는 DB 커넥션 풀(10개)이다.

## 2. 시나리오

세션 1개(`load-test/chat/chat-session.js`)는 아래 순서로 진행된다.

1. 로그인 `POST /api/users/login`
2. 방 목록 `GET /api/chat/rooms`
3. 새 채팅 시작 `POST /api/chat/messages` → 견적 카드 확인
4. 같은 방에 메시지 4번 `POST /api/chat/rooms/{roomId}/messages` → 매번 견적 카드 확인
5. 메시지 목록 `GET /api/chat/rooms/{roomId}/messages`

세션마다 다른 사용자를 쓴다(5001번부터 순서대로).

| | 스모크 | 부하 | 스트레스 |
|---|---|---|---|
| 스크립트 | `chat-smoke.js` | `chat-load.js` | `chat-stress.js` |
| 방식 | 가상 사용자 3명 반복 | 분당 25세션 시작(`constant-arrival-rate`) | 분당 25 → 375세션으로 단계적으로 올림(`ramping-arrival-rate`) |

## 5. AI를 기다리는 동안 DB 커넥션을 붙잡지 않는가

### 근거 1. 커넥션 한 번 사용 시간 (가장 직접적인 근거)

`hikaricp_connections_usage_seconds` 히스토그램을 테스트 직전(`results/chat/chat-load-hikari-before.txt`)과 직후(`results/chat/chat-load-hikari-after.txt`)에 기록하고, 그 차이를 계산했다.

| 커넥션 한 번 사용 시간 | 횟수 | 비율 |
|---|---|---|
| 전체 | 2,922 | 100% |
| 0.1초 이하 | 2,157 | 73.8% |
| 1.07초 이하 | 2,716 | 92.9% |
| 2.15초 이하 | 2,893 | 99.0% |
| 3.58초 초과 | 15 | 0.5% |
| 4.29초 초과 (가장 긴 칸: 4.29~5.73초) | 10 | 0.3% |
| 5.73초 초과 | **0** | 0% |

- 메시지 1건은 LLM을 2번 부르고, 두 번을 합치면 최소 7초다.
- 커넥션을 LLM 대기 내내 붙잡았다면, 메시지 630건마다 7초 넘는 사용이 1번씩 생겨야 한다. 실제로는 5.73초를 넘은 경우가 **0건**이었다.
- LLM 한 번(3.5~6초) 동안만 붙잡았다고 해도 630건이 모두 3.5초를 넘어야 한다. 실제로 3.58초를 넘은 경우는 15건뿐이었다.
- 이 15건은 견적 발급이 느렸던 경우로 본다.
  - 테스트 직후에 읽은 최대값(`_max`)이 견적 발급 5.49초, 커넥션 사용 5.56초로 거의 같다.
  - 다만 Micrometer의 `_max`는 테스트 전체가 아니라 읽은 시점 기준 최근 약 2~3분 안의 최대값이다. 그래서 둘을 비교하는 근거로만 쓰고, 횟수는 히스토그램(누적)으로 센다.

### 근거 2. 처리 중인 채팅 수와 쓰고 있는 커넥션 수

채팅 요청은 평균 19.3건이 동시에 처리됐다. 같은 시점에 쓰고 있던 DB 커넥션은 평균 2.0개였고, 커넥션을 기다린 요청은 한 번도 없었다. 처리 중인 요청 대부분은 커넥션 없이 LLM 응답을 기다리고 있었다.

### 근거 3. 처리량

- 커넥션을 메시지 처리 내내(10.7초) 붙잡는다면, 커넥션 10개로 처리할 수 있는 메시지는 초당 10 ÷ 10.7 = 0.93건이다.
- 이번 테스트는 초당 2.1건을 보냈고, 실패 0건·커넥션 대기 0으로 처리했다.

## 6. 테스트 중 확인한 점

- **채팅 응답 p95(12.6~12.7초)가 기준 13초에 가깝다.** fake LLM 지연을 2번 합친 값(7~12초)과 견적 발급(평균 1.13초)이 더해진 결과다.
- **견적 발급이 혼자 보낼 때보다 느렸다.**
  - 메시지 1건만 보냈을 때 0.95초였고, 테스트 중 평균은 1.13초였다. 테스트 직후에 읽은 최근 약 2~3분의 최대값은 5.49초였다.
  - 이 시간 동안은 DB 커넥션을 쓴다.
  - 쓰고 있는 커넥션이 순간적으로 9개(최대 10개)까지 올라간 것도 이 구간이다.
  - 스트레스 테스트에서 트래픽을 올리면 이 구간이 커넥션 대기의 원인이 될 수 있다.

   - 커넥션 10개를 모두 쓰고, 최대 74건이 커넥션을 기다렸다.
   - 실패는 없었지만 응답 p95가 12.2초에서 34.2초로 늘었다.
   - 견적 발급은 커넥션 1개를 평균 1~2.5초 쓴다. 그래서 커넥션 10개로는 초당 약 4~10건만 처리할 수 있다.
2. **×6 (12.5 RPS): Tomcat 스레드 200개가 다 찼다.**
   - 커넥션을 기다리는 요청이 스레드를 붙잡고 있어서 스레드도 다 찼다.
   - 커넥션을 30초 안에 못 얻은 요청이 500으로 실패하기 시작했고, 이 단계에 보낸 메시지의 25.4%가 실패했다.
3. **×9 이상: 실패율이 51~95%로 올랐다.**
   - 성공한 메시지는 초당 3.8건을 넘지 못했다.
   - 이 환경에서 처리할 수 있는 최대치는 메시지 **초당 약 3~4건(목표의 약 1.5~1.8배)**이다.

### 7-5. 확인한 점

- **트래픽이 몰려도 AI 대기 중에 커넥션을 붙잡지 않았다.**
  - 테스트 중 커넥션을 12,209번 썼다. 가장 긴 사용은 4.29~5.73초 칸의 12건이다.
  - 5.73초를 넘은 경우는 0건이다.
  - 커넥션이 부족했던 것은 견적 발급 때문이다. LLM 대기와는 관계없다.
- **채팅 과부하가 다른 API에도 영향을 줬다.**
  - 로그인 p95는 0.19초에서 ×3에 9.3초로, 방 목록 p95는 0.01초에서 3.4초로 늘었다.
  - 이 API들은 채팅과 같은 DB 커넥션 풀과 Tomcat 스레드를 쓰기 때문이다.
- **메시지 시간 예산이 동작했다.**
  - 503건은 커넥션 대기로 메시지 시간 예산(`LlmTimeBudget`)이 모자랐다. 이 경우 안내 문장 LLM 호출을 생략하거나 중간에 끊었다.
  - 견적 카드는 고정 문구로 저장해 201로 응답했다 (`zelo_chat_explain_degraded_total{code="AI_002"}` 503건).
- **서킷은 계속 closed였다.** 실패 원인이 LLM이 아니라 DB였기 때문에, LLM 서킷이 열리지 않은 것이 맞다.
- **로컬 환경의 한계가 있다.**
  - k6, 앱, Postgres가 한 노트북(8코어)에서 같이 돌았고, 테스트 끝에는 전체 CPU 사용률이 99.8%였다.
  - 견적 발급이 1.13초에서 2.52초로 느려진 데는 CPU 부족도 섞여 있다.
  - 서버를 따로 둔 환경(AWS)에서는 무너지는 단계가 달라질 수 있다.
