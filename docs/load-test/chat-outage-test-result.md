# 채팅 LLM 장애·복구 테스트 결과

- 실행일: 2026-11-04
- 브랜치: `feat/393-chat-seed`
- 확인하려는 것: **AI가 응답하지 않으면 실패 안내를 바로 하고, AI가 회복되면 다시 답하는가**
- 결과: **통과했다.**
  - 장애가 나고 12.8초 만에 서킷이 열렸고, 그 뒤로는 실패 안내를 평균 0.03초 만에 보냈다.
  - AI를 정상으로 되돌린 지 13.2초 만에 서킷이 스스로 닫혔고, 그 뒤 요청은 모두 견적 카드를 받았다.

## 1. 실행 환경

| 항목 | 값 |
|---|---|
| 앱 | 로컬 1대, `performance` 프로필 |
| DB | Postgres 16 (docker), Hikari 커넥션 최대 10개 |
| LLM | fake. 처음에는 모든 호출을 **15초** 뒤에 답하게 둠 (시간 제한 12초보다 길어 모두 시간 초과) |
| LLM 판단 | 항상 장보기 요청(`plan-intent=SHOPPING_REQUEST`). 성공하면 견적 발급까지 간다 |
| 데이터 | 사용자 시드 5,001~5,500번(500명), 채팅방 105,000개·메시지 1,050,000건, 상품 약 10만 개 |

앱 실행 명령:

```bash
JWT_SECRET=... OPENAI_API_KEY=fake ./gradlew bootRun --args='--spring.profiles.active=performance --zelo.llm.fake.plan-intent=SHOPPING_REQUEST --zelo.llm.fake.mode=DELAY --zelo.llm.fake.delay=15s --zelo.seed.enabled=true --zelo.seed.load-test.enabled=true --zelo.delivery.scheduler.enabled=false'
```

LLM 관련 설정(`application.yaml`, `zelo.llm`):

| 설정 | 값 | 뜻 |
|---|---|---|
| `timeout` | 12초 | LLM 호출 1번을 기다리는 최대 시간 |
| `retry.max-attempts` / `wait-duration` | 2 / 0.5초 | 실패하면 0.5초 쉬고 1번 더 시도 |
| `circuit-breaker.sliding-window-size` | 10 | 최근 시도 10번으로 실패율을 계산 |
| `circuit-breaker.minimum-number-of-calls` | 5 | 시도가 5번 쌓여야 판단 |
| `circuit-breaker.failure-rate-threshold` | 50% | 실패율이 이 이상이면 서킷을 연다 |
| `circuit-breaker.wait-duration-in-open-state` | 30초 | 열린 뒤 30초 동안 LLM을 부르지 않는다 |
| `circuit-breaker.permitted-number-of-calls-in-half-open-state` | 3 | 30초 뒤 시험 호출 3번으로 닫을지 정한다 |

## 2. 시나리오 (`load-test/chat/chat-llm-outage.js`)

요청은 **새 채팅 시작(`POST /api/chat/messages`) 하나만** 반복한다. 사용자 500명은 시작 전에 미리 로그인해 둔다.

| 구간 | 시간 | 속도 | 하는 일 |
|---|---|---|---|
| 장애 (`outage`) | 0~120초 | 초당 10건 (목표 2.1 RPS의 약 5배) | fake LLM이 15초 지연이라 모든 LLM 호출이 시간 초과 |
| 복구 전환 (`recover`) | 120초에 1번 | | `POST /api/fake/llm/mode`로 fake LLM을 정상 지연(3.5~6초)으로 바꿈 |
| 복구 (`recovery`) | 120~270초 | 초당 2건 (목표 수준) | 서킷이 닫힌 뒤 견적 카드가 다시 오는지 확인 |

- **장애 구간이 초당 10건인 이유:** 서킷이 없다면 요청마다 최대 24.5초(12초 × 2 + 0.5초)를 기다린다. 그러면 동시 요청이 10 × 24.5 = 245건으로 Tomcat 스레드 200개를 넘는다. 서킷이 이것을 막는지 보려는 것이다.
- **복구 구간이 초당 2건인 이유:**
  - 복구 뒤에는 메시지마다 견적 발급까지 간다.
  - 스트레스 테스트에서 견적 발급(DB 커넥션) 한계가 초당 3~4건이었다.
  - 초당 10건을 그대로 보내면 서킷과 관계없는 DB 커넥션 부족(500)이 섞인다.
- **통과 기준**
  - 새 채팅 실패율 < 1%. 견적 카드(201)와 실패 안내(502·503·504)만 정상으로 보고, 그 밖의 상태는 실패로 센다.
  - 응답이 견적 카드 또는 FALLBACK인 비율 > 99%.
  - 복구 전환 호출 성공.

## 4. 서킷 상태 변화 (앱 로그 `LLM 서킷 상태 변경`)

첫 요청을 보낸 시각(17:04:35)을 0초로 둔다.

| 시각 | 경과 | 상태 변화 | 일어난 일 |
|---|---|---|---|
| 17:04:35 | 0초 | closed | 초당 10건 시작. 요청마다 LLM을 부르고 12초를 기다림 |
| 17:04:47.8 | **12.8초** | closed → **open** | 첫 요청들이 12초 시간 초과로 실패. 실패 5번이 쌓이자 바로 열림 |
| 17:05:17.9 | 42.9초 | open → half_open | 30초가 지나 시험 호출 3번 |
| 17:05:30.1 | 55.1초 | half_open → open | 시험 3번도 12초 뒤 시간 초과. 다시 30초 차단 |
| 17:06:00.1 | 85.1초 | open → half_open | 시험 호출 3번 |
| 17:06:12.3 | 97.3초 | half_open → open | 아직 장애라 다시 실패 |
| 17:06:35 | **120초** | open | fake LLM을 정상(3.5~6초)으로 바꿈 |
| 17:06:42.4 | 127.4초 | open → half_open | 시험 호출 3번. 이번에는 성공 |
| 17:06:48.2 | **133.2초** | half_open → **closed** | 서킷이 닫힘. 그 뒤 요청은 모두 견적 카드 |

- 장애 동안 30초 열림 → 약 12초 시험 → 다시 열림을 2번 반복했다.
- 장애 구간 내내 LLM 시도는 118번뿐이었다. 첫 묶음과 반쯤 열림 때 시험 호출만 LLM에 갔다. 나머지 1,211번은 서킷이 막았다(`zelo_llm_attempt_seconds{outcome="AI_008"}`).
- **복구까지 걸린 시간은 13.2초다(120초 → 133.2초).**
  - 이 시간은 복구 순간 서킷이 열린 지 얼마나 지났는지에 따라 달라진다.
  - 가장 늦으면 30초(열림 대기) + 시험 호출 시간(약 6초)이다.

## 7. 알게 된 것

1. **AI 장애 때 서킷이 사용자 대기와 서버 자원을 지켰다.**
   - 장애 후 12.8초 만에 열렸다. 그 뒤 실패 안내는 0.03초였고, Tomcat 스레드는 최대 98개(200개 중)에서 다시 0~4개로 줄었다.
2. **AI가 회복되면 사람이 손대지 않아도 다시 답했다.**
   - 30초마다 시험 호출을 보내다가, 회복 후 첫 시험이 성공하자 닫혔다(복구 후 13.2초).
   - 그 뒤 요청은 모두 견적 카드(201)를 받았다.
3. **재시도는 서킷이 열린 뒤에는 LLM을 다시 부르지 않았다.**
   - 첫 요청들의 재시도는 서킷에 막혀 바로 실패 안내로 끝났다. 그래서 응답 시간이 24.5초가 아니라 12.5초였다.
4. **장애 중 첫 12초는 막을 수 없다.**
   - 서킷은 실패가 5번 쌓여야 열리고, 첫 실패는 시간 제한(12초)이 지나야 나온다.
   - 그래서 장애 직후 약 100건은 12.5초를 기다렸다. 이 시간을 줄이려면 시간 제한(`timeout`)을 줄여야 한다. 그러면 정상일 때 느린 응답도 실패로 처리하게 된다.
