# 채팅 부하·스트레스 테스트 결과 (새 기준 DAU 5만)

## 조건
- 기준: DAU 5만 중 피크 1시간에 1만 명, 그중 견적을 받는 50%(전체 시나리오 B 30% + C 20%)가 채팅 세션 1번, 안전계수 1.5
  - 1만 × 50% ÷ 60분 × 1.5 = **세션 분당 125개, 메시지 10.4 RPS** (예전 기준은 분당 25개, 2.1 RPS)
  - 견적 테스트(`load-test/quote`)와 같은 비율이다
- 코드: `test/411-product-quote-load-test` 위 (견적 후보만 조회하는 수정 포함, 견적 발급 0.8초 → 0.33초)
- 서버: performance 프로필, 스케줄러 끔, DB 커넥션 10개, Tomcat 스레드 200개
- LLM: fake, 호출 1번에 3.5\~6초. 메시지 하나는 LLM 2번(메뉴 계획 + 견적 설명)이라 약 9.5초
- 세션: 로그인 → 방 목록 → 첫 메시지 → 이어서 4번 → 메시지 목록 (메시지 5건, 약 48초)
- 사용자: 5,001\~10,000번 (견적 테스트는 10,001\~15,000번)
- k6·서버·DB를 PC 한 대(도커)에서 같이 돌렸다
- 결과 파일: `docs/load-test/results/chat/dau50k/`

## 부하 (분당 125세션, 5분)
| 항목 | 값 |
|---|---|
| 보낸 세션 / 메시지 | 625개 / 3,125건 (10.4 RPS) |
| 첫 메시지 p95 | 11.3s (기준 13s) |
| 이어서 보낸 메시지 p95 | 11.46s (기준 13s) |
| 실패 / checks | 0% / 100% |
| 서버 처리 시간 (채팅 시간 − LLM 시간) | 메시지 1건에 평균 0.17s |
| DB 커넥션 사용 (평균 / 최대) | 1.6 / 7, 대기 0 / 0 |
| 커넥션 얻는 시간 / 잡는 시간 (평균) | 2.7ms / 40ms |
| Tomcat 바쁜 스레드 (평균 / 최대) | 86 / 106 (200개 중) |

- 메시지 시간 거의 전부가 LLM 기다리는 시간이다. 서버 자체 처리는 0.17초
- 커넥션 잡는 시간 40ms는 견적 발급만의 시간이 아니라 이 테스트의 모든 커넥션 대여(메시지 저장, 조회 등 포함) 1회의 평균이다. 예전 기준 부하에서는 견적 발급이 커넥션 1개를 1.13초 잡았다. 수정 뒤 견적 발급 자체의 값은 견적 테스트 결과(`load-test/quote/README.md`)로 본다

## 스트레스 (단계별)
단계는 요청을 보낸 시각(응답 시각 − 걸린 시간)으로 나눴다. ×1 단계는 세션이 막 시작되는 구간이라 메시지 RPS가 목표보다 낮게 나온다

| 단계 | 메시지 RPS | p50 | p95 | 최대 | 못 보낸 세션 | Tomcat 바쁜 스레드 (평균/최대) | 커넥션 사용 (평균/최대) | 커넥션 대기 (평균/최대) |
|---|---|---|---|---|---|---|---|---|
| ×1 | 8.3 | 9.7s | 11.4s | 12.0s | 0 | 75 / 104 | 1.5 / 3 | 0 / 0 |
| ×1.5 | 14.2 | 9.6s | 11.3s | 12.0s | 0 | 134 / 155 | 2.2 / 5 | 0 / 0 |
| ×2 | 19.2 | 9.8s | 11.6s | 12.6s | 0 | 184 / **200** | 3.8 / 10 | 0.7 / 11 |
| ×2.5 | 20.6 | 12.0s | 15.7s | 19.5s | 31 | **200 / 200** | 6.1 / 10 | 6.4 / 33 |
| ×3 | 18.4 | 18.3s | 21.9s | 24.3s | 142 | **200 / 200** | 7.2 / 10 | 29.1 / 69 |

- 전체 실패(`http_req_failed`) 0건, checks 100%. 처리하지 못한 만큼 응답이 늦어지고 k6가 세션을 못 보냈다(173개)
- **×2까지 버팀**: p95 11.6s로 목표와 같다. 다만 Tomcat 스레드가 순간 200개에 닿기 시작한다
- **×2.5부터 무너짐**: Tomcat 스레드 200개가 계속 다 차고 처리량이 메시지 약 20 RPS에서 더 오르지 않는다. ×3에서는 오히려 18.4 RPS로 줄었다
- 최대 처리량: 메시지 약 **20 RPS** (목표 10.4 RPS의 약 2배)

## 원인
- 메시지 하나가 LLM을 약 9.5초 기다리는 동안 Tomcat 스레드 하나를 잡는다
  - 동시 메시지 = 메시지 RPS × 9.5초 → 20 RPS × 9.5초 ≈ 190개로 Tomcat 스레드 200개에 닿는다
  - 처리 중인 채팅 요청(`zelo_chat_inflight`)도 ×2.5·×3에서 196\~200개로 Tomcat 바쁜 스레드와 같았다
- DB 커넥션은 원인이 아니다
  - 커넥션 대기는 Tomcat이 다 찬 ×2.5부터 생겼다. 스레드 200개가 한꺼번에 몰려 커넥션을 달라고 하는 결과로 본다
  - 예전 기준 스트레스에서는 ×3(메시지 약 6 RPS)에서 견적 발급이 커넥션을 2.5초 잡아 커넥션 10개가 먼저 찼다. 견적 수정 뒤에는 한계가 메시지 약 3.8 RPS → 20 RPS로 올랐고, 막히는 곳이 DB 커넥션에서 Tomcat 스레드로 바뀌었다
